# Squat Voice Coaching — Implementation Spec

**For:** Dev team maintenance and extension
**Status:** Implemented for Squat, using pre-generated WAV assets
**Depends on:** Gemini-generated WAV files in `assets/audio/squat/`, `audioplayers`, Squat state machine, `ResultIssues`

---

## 1. What Exists Today (Do NOT Delete)

### ResultIssues (lib/exercise/exercise_base.dart)

```dart
class ResultIssues {
  Map<String, String> feedback = {};                  // per-frame, cleared every frame
  Map<String, Map<String, String>> instructions = {}; // phase -> {type -> message}

  void addInstruction(String phase, String type, String message) { ... }
  void clear() { ... }
}
```

- `feedback{}` is per-frame. Metrics write live values here, such as `Back: Chest up!` and `Sync: Drive chest up!`.
- `instructions{}` survives across frames until Squat clears or overwrites it. Squat writes current phase status here.
- Voice reads from the same exercise-layer data. Voice does **not** recalculate landmarks and does **not** create its own pose analysis layer.

### FaultRecord (lib/exercise/fault_record.dart)

```dart
class FaultRecord {
  final String phase;
  final String type;
  final String message;
  final bool affectsForm;
  final String? voiceMessage;
  final int priority; // lower = higher priority
}
```

- `voiceMessage` is the raw post-rep candidate generated by metrics.
- `priority` decides which post-rep cue wins when multiple voiced faults exist.
- Silent faults (`voiceMessage == null`) still affect form, but do not block lower-priority voiced faults.

### Squat state machine (lib/exercise/squat/squat.dart)

```dart
enum SquatState { standing, descending, bottom, ascending }
```

Current Squat responsibilities:

- `_updatePhaseInstructions()` writes the current status text.
- `_completeRep()` increments `repCount`, evaluates rep-end faults, and stores:
  - `lastRepFaultVoiceMessages`
  - `lastRepTopVoiceMessage`
  - `lastRepTopVoicePriority`
  - `lastRepWasClean`
- `Squat.topVoicedFault(...)` and `Squat.orderedUniqueVoiceMessages(...)` centralize post-rep voice selection.
- `Squat.hasCompletedBottomHold` lets the coach derive `Đứng lên` while the state is still `bottom`.

### Runtime voice wiring (lib/screens/exercise/active_exercise_page.dart)

- `ActiveExercisePage` creates `SquatVoiceCoach` in `initState()` when `widget.exercise is Squat`.
- `_processSquatVoiceFrame(...)` forwards:
  - `exercise`
  - `repCount`
  - `hasPose`
  - `_feedback`
- Forwarding happens on pose frames, no-pose frames, and completed frames.

**Keep this boundary.** The screen should forward runtime context only. It should not infer rep completion, phase priority, or fault priority.

### Existing voice service boundary (lib/services/squat_voice_coach.dart)

```dart
abstract class SquatVoicePlayer {
  Future<void> speak(String text);
  void clearQueue();
  void clearPendingButKeepCurrent();
  void dispose() {}
}
```

- `SquatVoiceCoach` owns gating, cooldown, priority, and queue policy.
- `SquatVoicePlayer` keeps playback replaceable in tests.
- The default runtime player is `_SquatAssetVoicePlayer`, which delegates to `QueuedAssetVoicePlayer`.

### 2.2 QueuedAssetVoicePlayer (lib/services/queued_asset_voice_player.dart)

Thin local-audio playback wrapper around `audioplayers`.

Responsibilities:

- keep a FIFO queue of phrase text
- play one audio file at a time
- support `clearQueue()` by stopping current playback
- support `clearPendingButKeepCurrent()` by dropping queued phrases only
- verify asset existence with `rootBundle.load(...)`
- log and skip missing phrase mappings or missing files

This player does **not** call Viettel, Gemini, HTTP, or any runtime TTS API.

## 3. Runtime Path

```text
Camera frame
  -> ExerciseBase.processPose() / processNoPoseFrame()
  -> Squat.checkingPose()
  -> Squat._updatePhaseInstructions() / Squat._completeRep()
  -> ActiveExercisePage._processSquatVoiceFrame(...)
  -> SquatVoiceCoach.processFrame(...)
  -> QueuedAssetVoicePlayer.speak(...)
  -> audioplayers AssetSource(audio/squat/{file}.wav)
```

Key rules:

1. Metrics never call audio directly.
2. UI never decides which voice cue wins.
3. Squat computes state, faults, and rep completion before voice runs.
4. `SquatVoiceCoach` decides speech order.
5. `QueuedAssetVoicePlayer` only plays local assets. Missing assets are skipped, not synthesized.

## 4. Voice Logic for Squat

### 4.1 Voice layers

| # | Layer | Trigger | Source | Queue behavior |
|---|---|---|---|---|
| 1 | Completion | `exerciseState == completed` | `exerciseState`, `repCount` | clear pending, optionally speak final outcome, then `Hoàn thành bài tập` |
| 2 | Silent gate | not activated, paused, or no pose | `exerciseState`, `isPaused`, `hasPose` | no speech |
| 3 | Ready countdown | first active frame only | `_didAnnounceReady == false` | `clearQueue()`, then `3`, `2`, `1`, `Sẵn sàng` |
| 4 | Initial descent cue | first active frame if phase is standing | phase phrase | queue `Xuống` after ready countdown |
| 5 | Rep outcome | `repCount > _lastRepCount` | Squat rep-end fields | clear pending, speak count, then clean or corrective |
| 6 | Phase cue | phase phrase changed | `instructions[currentPhase]['Status']` + bottom hold | speak if phase gap allows |
| 7 | Live fault cue | eligible live trunk/sync fault | `feedback['Back']`, `feedback['Sync']` | trunk cue can clear pending and speak next |

### 4.2 Silent gates

No Squat voice should fire when:

1. `exercise.exerciseState != ExerciseState.activated` and the exercise is not completed
2. `exercise.isPaused == true`
3. `hasPose == false`

Exception:

- completion speech still runs when `exercise.exerciseState == ExerciseState.completed`

Resume behavior:

- pause/no-pose resets `_lastPhasePhrase`, so the current phase cue may replay after resume
- pause/no-pose does **not** reset `_didAnnounceReady`, so the ready countdown does not replay mid-set

### 4.3 Phase cues

Squat writes these status strings:

| Squat state | Status written by Squat | Spoken phrase |
|---|---|---|
| `standing` | `Xuống` | `Xuống` |
| `descending` | `Going Down...` | silent |
| `bottom` while hold remains | `Hold! {n}s` | `Giữ` |
| `bottom` after hold completes | `Đứng lên` | `Đứng lên` |
| `ascending` | `Đứng lên` | `Đứng lên` |

Special rule:

- if `Squat.hasCompletedBottomHold == true` while state is still `bottom`, voice derives `Đứng lên` immediately
- this release cue can bypass the normal 250ms phase gap
- this release cue suppresses live fault speech on the same frame

### 4.4 Live fault cue

Current live voice is intentionally narrow.

| Source | Condition | Spoken phrase | Cooldown |
|---|---|---|---|
| `feedback['Back']` | contains `Chest up` | `Ưỡn ngực lên` | 3000ms |
| `feedback['Sync']` | contains `chest up` | `Ưỡn ngực lên` | 3000ms |

Rules:

- `Ưỡn ngực lên` is the only live corrective phrase today.
- The same live phrase is spoken at most once per rep.
- The same live phrase also has a 3000ms cooldown.
- If the bottom release cue unlocks on the same frame, `Đứng lên` wins.
- Depth feedback (`Go Lower`) is currently silent during the rep.

### 4.5 Rep outcome

On rep increase:

```dart
clearPendingButKeepCurrent();
speak('$repCount');

if (lastRepWasClean) {
  speak('tốt');
} else {
  maybeSpeakOnePostRepCorrective();
}
```

Clean rep:

- speaks rep count
- then speaks `tốt`

Faulty rep:

- speaks rep count
- then optionally speaks one post-rep corrective

Completed set:

- if completion frame also includes a new rep, count is not repeated as a separate number in the completion branch
- `Hoàn thành bài tập` is spoken once per set

## 5. Post-Rep Corrective Selection

### 5.1 Fault priority

`SquatFaultVoicePriority` is the source of truth:

```dart
class SquatFaultVoicePriority {
  static const int heelRise = 0;
  static const int depth = 1;
  static const int trunkLean = 2;
  static const int hipShoulderSync = 3;
  static const int tempo = 4;
  static const int trunkLeanBackward = 5;
}
```

### 5.2 Metric-to-voice mapping

| Metric | Raw `voiceMessage` | Priority | Spoken post-rep |
|---|---|---|---|
| HeelRise | `Giữ gót chân` | 0 | `nhớ giữ gót chân` |
| Depth | `Xuống thấp hơn` | 1 | `nhớ xuống thấp hơn` |
| TrunkLean forward | none | 2 | live only |
| HipShoulderSync | none | 3 | live only |
| Tempo | `Chậm lại` | 4 | `nhớ chậm lại` |
| TrunkLean backward | none | 5 | silent |

### 5.3 Selection algorithm

At rep completion, Squat:

1. completes depth and tempo rep-end evaluation
2. collects faults from all metrics
3. filters faults with non-empty `voiceMessage`
4. sorts by `priority`, then `type`, then `message`
5. stores only the top voiced fault in `lastRepTopVoiceMessage`

Then `SquatVoiceCoach`:

1. ignores post-rep if `lastRepWasClean == true`
2. ignores post-rep if `lastRepTopVoiceMessage` is null/empty
3. converts raw text to `nhớ ...`
4. suppresses if the same final post-rep phrase was used on the immediately previous rep
5. suppresses if the same raw phrase was spoken live within 1500ms
6. speaks the final post-rep phrase

Important:

- only one post-rep corrective is spoken
- heel rise wins over depth and tempo
- depth wins over tempo
- silent faults do not block lower-priority voiced faults
- post-rep cooldown is phrase-based

### 6.3 Audio generation

Squat audio is generated outside this app, then copied into the repo as WAV files.

Current policy:

1. Generate with the external Gemini TTS workflow.
2. Export as `.wav`.
3. Keep names stable and lowercase snake_case where possible.
4. Place files in `assets/audio/squat/`.
5. Add every emitted phrase to `SquatVoiceAssets.files`.
6. Run `test/services/squat_voice_assets_test.dart` to verify all catalog entries are bundled.

Do **not** add runtime Gemini or Viettel calls to the mobile app for Squat voice.

- [ ] no voice fires before activation completes

- [ ] ready countdown fires once per set

### Phase cues

- [ ] `standing` status `Xuống` produces `Xuống`
- [ ] `descending` status `Going Down...` is silent
- [ ] bottom hold status maps to `Giữ`
- [ ] bottom release maps to `Đứng lên`
- [ ] bottom release can speak while state is still `bottom`
- [ ] bottom release suppresses live fault on the unlock frame
- [ ] pause/no-pose reset allows current phase cue to replay after resume

### Live faults

- [ ] `feedback['Back'] = Chest up!` produces `Ưỡn ngực lên`

- [ ] trunk cue can preempt normal phase speech
- [ ] same live phrase does not repeat within the same rep
- [ ] same live phrase does not repeat faster than 3000ms

### Rep outcome

- [ ] every rep increase speaks the rep number once
- [ ] clean rep speaks `tốt` after count
- [ ] faulty rep does not speak `tốt`
- [ ] faulty rep may speak exactly one post-rep corrective
- [ ] heel rise beats depth and tempo
- [ ] depth beats tempo
- [ ] same post-rep phrase does not repeat on consecutive reps
- [ ] live phrase within 1500ms can suppress matching post-rep phrase

### Completion

- [ ] `Hoàn thành bài tập` fires once per set
- [ ] completion does not replay on later pose or no-pose frames
- [ ] completion branch ignores stale live feedback

### Assets

- [ ] every entry in `SquatVoiceAssets.files` loads from `rootBundle`
- [ ] every emitted phrase has a WAV file
- [ ] missing file logs and skips instead of calling network TTS
- [ ] `assets/audio/squat/` remains listed in `pubspec.yaml`

## 8. Safe Extension Rules

When extending Squat voice:

1. Do not move audio calls into metrics.
2. Do not teach `ActiveExercisePage` to infer fault priority.
3. Add new spoken phrases to both emitting code and `SquatVoiceAssets`.
4. Add the matching `.wav` file under `assets/audio/squat/`.
5. Update `test/services/squat_voice_assets_test.dart` if the catalog shape changes.
6. Keep completion and rep count higher priority than phase and live-fault cues.
7. Preserve the bottom-release special case unless product deliberately changes it.
8. Keep Squat voice local-only. No Viettel/Gemini runtime fallback.

---

## 9. Known Gaps

1. Only one post-rep corrective is spoken, even though `lastRepFaultVoiceMessages` stores the full ordered list.
2. Live voice only handles chest-up cues from `Back` and `Sync`.
3. There is no Squat-specific mute setting yet.
4. There is no per-exercise volume setting yet.
5. Counts above `15` are not in the current Squat WAV catalog.

---

## 10. Implementation Order for Future Work

1. **Squat complete:** local WAV playback, phrase catalog, ready/phase/live/rep/post-rep/completion logic.
2. **Add settings:** mute and volume, ideally shared across exercise voice services.
3. **Extend counts if needed:** add `16.wav` through `30.wav` before allowing higher-rep Squat sets.
4. **Generalize carefully:** extract shared player/catalog patterns only after the next exercise needs local WAV voice.
5. **Migrate other exercises:** remove `ViettelTTSService` from shared exercise voice paths once each exercise has its own local asset catalog.
