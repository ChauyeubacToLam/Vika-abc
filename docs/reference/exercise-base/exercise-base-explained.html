00 Orientation

The big picture — read this first

Before any code: what is this file, in one breath.

🧒 Like you’re five

ExerciseBase is a fill-in-the-blanks worksheet for exercises. Every exercise (Squat, Plank, Cobra…) is a different worksheet, but they all share the same printed parts: “find the person,” “wait for them to get ready,” “count reps,” “notice if they walk away,” “tell the coach what to say.” ExerciseBase prints all those shared parts once. Each real exercise only fills in the blanks that are special to it — like “what does the ‘down’ position look like?”

The phone’s camera AI (Google ML Kit) looks at each video frame and drops 33 dots on your body — shoulder, elbow, hip, knee, and so on. These dots are called pose landmarks. Each dot carries: x, y (where on screen), z (how near/far), presence (“is this joint really there?”) and visibility (“can we actually see it?”). ExerciseBase’s whole job is to turn a stream of these dots into “rep counted,” “good form,” “paused,” etc.

Two mental models to hold

1. The lifecycle — an exercise is a 3-square board game. You only ever move forward:

notActivated
“Get into position.” Looking for a person & waiting for the ready pose.
→
hold the start pose
still for 3 seconds
activated
The set is live. Counting reps, checking form, watching presence.
→
target reps reached
(requestStop())
completed
Set done. Show the summary; stop counting.

2. The heartbeat — a function called processPose() runs for every single camera frame (~30 times a second). Everything below is really just “what happens on each heartbeat.” Here’s the order it does things in:

Update FPS & timestamp
Stamp “now” once so the whole frame agrees on the time.
Smooth the dots
Run landmarks through the One Euro Filter so they stop jittering.
Sync presence
Is a human in frame? Confirm arrivals, start the auto-pause clock on exits.
Early exits
No person yet, or paused → return a status message and stop here.
Poke segmentation on trouble
Low presence / edge-of-frame / anomaly → ask the person-detector to re-check.
Detect facing & scale
Front or side view? How big on screen? (normalizes measurements.)
Safety check
Subclass can veto with a warning message → stop here.
Run the state machine
Advance the board game: activate, or count reps & check form, or finish.
Return feedback
Give the UI back [repCount, feedbackMap] or the final set summary.

🧒 Like you’re five

An enum is just “a short list of the only allowed answers.” ExerciseState is the 3 squares of the board game. CameraFacing is “which way is the person turned?” — facing the camera, turned to their left/right, at an angle, or we-can’t-tell.

The two numbers decide front-vs-side. The trick: when you face the camera your shoulders look wide; when you turn sideways they look narrow (one shoulder hides behind the other). So “shoulder width ÷ torso height” is big when facing you (> 0.57 → front) and small when sideways (< 0.35 → side). In between is “angled.”

🧠 Naming convention

The UPPER_SNAKE_CASE names would normally make Dart’s linter complain — that’s exactly what the // ignore_for_file: constant_identifier_names back on line 8 silences. It’s a deliberate house style for tuning constants.

abstract class ExerciseVoiceCoach {

    required ExerciseBase exercise,
    required int repCount,
    required bool hasPose,
    required Map<String, String> feedback,
  });

  Future<void> waitUntilIdle({
    Duration timeout = const Duration(seconds: 4),
  }) {
    return Future<void>.value();
  }

  void dispose();
}

🧒 Like you’re five

Think of it as a job description for “the trainer who talks.” To be hired, you must be able to: (1) processFrame — react every frame (say “2!”, “go lower”); (2) waitUntilIdle — “finish talking before we move on”; (3) dispose — pack up and shut off. Squat, Plank, Bird Dog each hire their own trainer that fits this description. The generic one lives at the bottom of this very file (section 16).

🧠 What is that “4” in waitUntilIdle?

It is not “wait 4 seconds before talking.” waitUntilIdle means “pause until the coach has finished saying everything already queued.” Duration(seconds: 4) is the most it will ever wait — a safety cap so a stuck audio clip can’t freeze the app; after 4s it gives up and moves on. And in this base version the body is literally return Future.value(), which finishes instantly — the default coach doesn’t actually wait at all, so here the 4 never even gets used. It’s just the default value that real coaches (Squat, Plank) rely on when they override this method with a real “wait for the audio queue to drain” body. Think of it as a fallback timeout, not a pause-before-speaking delay.

🧠 Why it’s here matters later

This little contract is imported by ~18 files (every exercise + the camera page). So even after we move the big generic coach out of this file, this interface has to stay somewhere importable. Keep this fact in your pocket for the refactor.

abstract class ExerciseBase {
  // Logger
  ExerciseLogger logger = ExerciseLogger();
  // Core state
  late PoseSmoother poseSmoother;
  int repCount = 0;

  /// Probability the landmark actually exists in the predicted skeleton.
  /// Drops cleanly when a person leaves frame; stays high for legitimately
  /// occluded landmarks such as the back leg in side-view squats.
  static const double MIN_PRESENCE = 0.7;

  /// Average presence below this threshold may indicate a faulty pose or that the
  /// person is not fully in frame.
  static const double AVG_LOW_PRESENCE_THRESHOLD = 0.35;

  /// Probability the landmark is unoccluded given that it exists.
  /// Used only as a secondary gate to reject fully extrapolated landmarks.
  static const double MIN_VISIBILITY = 0.3;

  /// Diagnostic-only bypass for auto-pause and pose-event backpressure.
  /// Keep false in production; enabling this disables pause paths while
  /// collecting continuity diagnostics.
  static const bool kDiagnosticMode = false;

  /// Master toggle for landscape orientation support across pose pipeline.
  /// When false, all paths fall through to portrait behavior identical to
  /// pre-spec production.
  static const bool kLandscapeRotationEnabled = true;

🧒 Like you’re five

repCount is the tally of reps. logger is the notebook. poseSmoother is the jitter-remover (late = “I’ll fill this in a moment, in the constructor”).

The two probabilities per dot: presence = “is this joint actually there?” and visibility = “can we see it, or is it hidden behind something?” A dot only counts as trustworthy if presence ≥ 0.7 and visibility ≥ 0.3.

🧠 The k flags are compile-time switches

kDiagnosticMode and kLandscapeRotationEnabled are static const — they’re read from other files (the camera page, the segmentation channel) as global on/off switches. kDiagnosticMode = true disables all auto-pausing so engineers can record continuous diagnostics. Leave it false in the app.

This is the pause-and-presence brain’s memory. Four “since when?” timestamps: _personSeenSince (when did a human first appear?), _personLostSince (when did they vanish?), _resumePresenceSince (how long have they been back?), and _holdStillStartedAt (when did they start holding the ready pose?). 🧠 Two kinds of pause

_isPaused = “are we paused?” _manualPause = “did the user tap pause (vs. they walked away)?” This split matters: if you walked away, standing back in frame auto-resumes. If you tapped pause, standing in frame must not sneakily un-pause you — only tapping resume does. That’s why two booleans, not one.

🔎 Deep dive: the “Person detection — only before activation” block (L273–286)

This is the “I haven’t confirmed a real person yet” gate. Piece by piece:

The outer if — notActivated && !_personConfirmed: only run this while we’re still in setup and we have not yet confirmed a person. From §9, remember someone only becomes “confirmed” after the selfie-segmentation AI has seen them continuously for 0.5s. That half-second wait is deliberate: it stops a one-frame flicker — a shadow, someone walking past — from falsely kicking off the exercise.

stableFor — how many milliseconds the person has been continuously seen so far (now − _personSeenSince, or 0 if nobody’s been seen yet). It’s purely a debug readout: the following line only stores it if (isDebugModeActive), so a developer can watch the number climb toward 500ms. In the shipped app, debug is off and these two lines do nothing.

The inner if (!_personConfirmed) — show the Vietnamese status “Đang tìm người… Vui lòng đứng trong khung hình” (“Looking for someone… please stand in the frame”) and return right away, bailing out of the entire frame. No reason to detect orientation, run the state machine, or count reps when we’re not even sure a person is there.

💡 A small redundancy in that block

The inner if (!_personConfirmed) is always true — the outer if already guaranteed it, and nothing in between changes _personConfirmed. So the inner check could be dropped and its body run directly. Harmless, but it makes the block look like it branches when it doesn’t.

🔎 Why return [repCount, resultIssues.feedback] when repCount is just 0?

You caught something real: before the set starts, repCount is 0, so why hand it back? Because processPose keeps one uniform return shape on every frame — always a 2-item list [repCount, feedback] (or the set summary once completed). The two callers both lean on that fixed shape, but in different ways (verified in the app code):

  • The camera page (active_exercise_page.dart) checks result.first is int && result[1] is Map purely as a shape guard, then reads result[1] for feedback. It shows the rep number from exercise.repCount directly — so here slot [0] is used only to validate that the return looks right.
  • The other pipeline (main.dart) actually reads result[0] as int as the live rep count every frame, comparing it to the previous value to notice a completed rep.

So the repCount here isn’t “logic” — it’s the honest current count, which is 0, handed back in the same slot every frame so a caller can blindly do reps = result[0], feedback = result[1] without ever branching on state. If the idle path returned a different shape, every caller would have to special-case it. The UI shows that 0 as your rep counter before you begin — which is correct.

💡 A real inconsistency this reveals

  bool _isLeftSide(Map<PoseLandmarkType, PoseLandmark>? smoothedLandmarks) {
    if (smoothedLandmarks == null) return false;

    const pairs = [
      [PoseLandmarkType.leftShoulder, PoseLandmarkType.rightShoulder],
      [PoseLandmarkType.leftElbow, PoseLandmarkType.rightElbow],
      [PoseLandmarkType.leftWrist, PoseLandmarkType.rightWrist],
      [PoseLandmarkType.leftHip, PoseLandmarkType.rightHip],
      [PoseLandmarkType.leftKnee, PoseLandmarkType.rightKnee],
      [PoseLandmarkType.leftAnkle, PoseLandmarkType.rightAnkle],

    int leftVotes = 0;
    int rightVotes = 0;
    for (final pair in pairs) {
      final leftLM = smoothedLandmarks[pair[0]];
      final rightLM = smoothedLandmarks[pair[1]];
      if (leftLM == null || rightLM == null) continue;

      final zDiff = leftLM.z - rightLM.z;
      double threshold = 0.01;
      if (zDiff.abs() > threshold) {
        if (zDiff < 0) {
          leftVotes++;
        } else {
          rightVotes++;
        }
      }
    }

    Map<PoseLandmarkType, PoseLandmark> smoothedLandmarks, {

    if (imageSize == null || imageSize == Size.zero) return false;

          landmark.y <= marginY ||

      }

    return outsideCount >= 2 || edgeCount >= 5;

🧠 Why abstract is powerful here

Because these are declared but empty, Dart won’t let anyone create an exercise that forgets one — it’s a compile error until every blank is filled. That’s the safety net that keeps 40+ exercises consistent with the shared pipeline above.

class HoldSecondsAccumulator {
  HoldSecondsAccumulator(Iterable<String> faultKeys) {
    for (final key in faultKeys) {
      _faultSeconds[key] = 0.0;
    }
  }

  static const int minFrameDeltaMs = 10;
  static const int maxFrameDeltaMs = 250;

  final Map<String, double> _faultSeconds = {};
  double _goodSeconds = 0.0;
  int? _lastHoldTickMs;

  double get goodSeconds => _goodSeconds;

  double faultSecondsFor(String key) => _faultSeconds[key] ?? 0.0;

  void reset() {
    _goodSeconds = 0.0;
    for (final key in _faultSeconds.keys) {
      _faultSeconds[key] = 0.0;
    }
    _lastHoldTickMs = null;
  }

  void resetTick() {
    _lastHoldTickMs = null;
  }

  void accumulate({
    required int elapsedMs,
    required Map<String, bool> faultingByKey,
    Iterable<String>? goodBlockingKeys,
  }) {
    for (final key in faultingByKey.keys) {
      _faultSeconds.putIfAbsent(key, () => 0.0);
    }

    final previous = _lastHoldTickMs;
    _lastHoldTickMs = elapsedMs;
    if (previous == null) return;

    final dtMs = elapsedMs - previous;
    if (dtMs < minFrameDeltaMs || dtMs > maxFrameDeltaMs) return;

    final seconds = dtMs / 1000.0;
    var hasFault = false;
    final goodBlockingSet = goodBlockingKeys?.toSet();
    var hasGoodBlockingFault = false;
    for (final entry in faultingByKey.entries) {
      if (!entry.value) continue;
      hasFault = true;
      if (goodBlockingSet == null || goodBlockingSet.contains(entry.key)) {
        hasGoodBlockingFault = true;
      }
      _faultSeconds[entry.key] = (_faultSeconds[entry.key] ?? 0.0) + seconds;
    }

    if (!hasFault || !hasGoodBlockingFault) {
      _goodSeconds += seconds;
    }
  }
}

🧒 Like you’re five

Imagine holding a plank. Every frame you say “how long since last frame?” and this adds that sliver of time to the right bucket: if your hips were sagging, add it to the “sag” fault bucket; if everything was fine, add it to “good.” At the end you know “held 22s good, 4s with sagging hips.” The 10ms/250ms guard throws away impossibly-tiny or suspiciously-huge gaps (app hiccups) so they don’t pollute the tally.

🧠 “goodBlocking” = which faults actually ruin the hold

Some faults are minor. goodBlockingKeys lets an exercise say “only these faults should stop me from earning ‘good’ seconds.” If you’re faulting but none of them are good-blocking, you still bank the second as good. Neat little bit of grading nuance.

💡 Placement

This class has zero dependency on ExerciseBase and 11 external users — a clean candidate to live in its own file (lib/exercise/hold_seconds_accumulator.dart). Pure lift, no behavior change.
