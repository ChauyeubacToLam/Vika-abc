00 Orientation

The big picture — read this first

One tap on a library card ends with a rep-counting camera session. Here is the whole relay in one breath, before any code.

🧒 Like you’re five

Think of a restaurant. The menu (the library shelf) shows you pretty pictures and names. When you point at one, a waiter looks up the recipe card (the ExerciseDefinition) that says how to actually cook it. But the portion sizes — how many reps, how many sets — aren’t on the menu or the recipe. They live in a separate printed price-list (the catalog) that the head office (Supabase) mails to every restaurant. The kitchen keeps a photocopy of that list on the wall so it works even when the internet is down. Cook = the live exercise the camera runs.

The three sources (this is the crux)

Almost everyone assumes “tap a card → run that card.” In reality three separate sources each own a different slice of the truth, and they’re stitched together only at launch time:

local · display

The shelf cards

What you see — title, icon, muscle tag. Hardcoded Dart lists. Purely cosmetic; carries only a lookup string, no real exercise.

lib/data/library_mock.dart

local · runtime

The definition registry

The recipe: colours, tips, camera hints, and the factory that builds the live exercise object. Hardcoded Dart list of ~40 entries.

lib/models/exercise_definition.dart

snapshot · numbers

The catalog

Sets / reps / seconds / Vietnamese name. A build-time export of a Supabase table, shipped as a JSON asset and read offline. The single source of truth for volume and display names.

assets/data/exercise_catalog.json

⚠️ The “online” part, honestly

There is no live network fetch anywhere on this path. The word “online” only means the catalog originates from a Supabase table — but a developer runs a generator script that downloads it into a JSON file (assets/data/exercise_catalog.json), and that file ships inside the app bundle. At runtime the app reads the bundled file, never the network. Supabase is hit live elsewhere (plan generation, profile) — just not when you launch an exercise from the library.

// Regenerates assets/data/exercise_catalog.json from the live Supabase
// `exercise_catalog` table — the single source of truth for default training
// volume. Run from the repo root:
//
//   dart run tool/generate_exercise_catalog.dart
//
// Reads SUPABASE_URL / SUPABASE_ANON_KEY from the environment or the bundled
// `.env`. Each catalog row is resolved to an ExerciseDefinition using the SAME
// order as WorkoutLaunchService._lookupLaunchDefinition (id → class_key →
// english_name). The tool FAILS LOUDLY (non-zero exit) if any row does not
// resolve to a definition, or violates the exactly-one-of-reps/seconds or
// sets >= 1 invariants — never silently drops a row.

const _select = 'id,class_key,vietnamese_name,english_name,'
    'is_form_checked,base_reps,base_seconds,base_sets';
const _outputPath = 'assets/data/exercise_catalog.json';

Future<void> main() async {
  final env = _loadEnv();
  final url = env['SUPABASE_URL'];
  final key = env['SUPABASE_ANON_KEY'] ?? env['SUPABASE_KEY'];

  final uri = Uri.parse('$url/rest/v1/exercise_catalog?select=$_select&order=id');
  final resp = await http.get(uri, headers: {
    'apikey': key,
    'Authorization': 'Bearer $key',
  });

  final rows = (jsonDecode(resp.body) as List).cast<Map<String, dynamic>>();

🧠 Why bake it in instead of fetching live?

Three wins. (1) Offline-safe — a user on the Hanoi metro with no signal can still start a squat set. (2) Deterministic — the numbers can’t shift mid-session because someone edited the table. (3) Validated — the generator fails loudly if a row is malformed or unresolvable, so a bad row is caught at build time on a developer’s machine, not as a crash on a user’s phone.

⚠️ The catch: it can go stale

If someone edits the Supabase table and forgets to re-run the generator, the app keeps shipping the old numbers. There is no runtime reconciliation on this path. Treat “edit the table” and “dart run tool/generate_exercise_catalog.dart + commit the JSON” as one atomic action.

/// Read-only source of default training volume (sets + rep/second target +
/// type), keyed by any exercise alias — catalog id, definition id, or class
/// key. This is the app's single source of truth for launch volume and for the
/// numbers shown on list/catalog surfaces.
///
/// [AssetCatalogSource] reads a build-time export of the Supabase
/// `exercise_catalog` table, so it works offline. The contract is deliberately
/// minimal and implementation-agnostic: a future SupabaseSyncedCatalogSource
/// can implement it as a drop-in replacement.
abstract class CatalogSource {
  /// Idempotent; safe to await repeatedly. Resolves once the catalog is ready.
  Future<void> ensureLoaded();

  /// Synchronous lookup by catalog id, definition id, or class key. Returns
  /// null if the catalog is not loaded yet or the id is unknown.
  ExerciseLaunchCatalogInfo? lookup(String id);

  /// Resolves many ids at once, keyed by the REQUESTED id so callers get back
  /// exactly what they asked for. Unknown ids are omitted.
  Map<String, ExerciseLaunchCatalogInfo> lookupMany(Iterable<String> ids);

  /// The shared instance. Reassign in tests, or to a runtime-synced source.
  static CatalogSource instance = AssetCatalogSource();
}

🧠 The seam for “make it live later”

Line 32 is the whole design bet: CatalogSource.instance is a swappable global. Today it’s AssetCatalogSource() (reads the JSON). The comment names a hypothetical SupabaseSyncedCatalogSource — the day Vika wants live catalog updates, you write that one class implementing the same three methods and reassign this line. Nothing else in the app changes. That’s why the “online → offline” decision is cheap to reverse.

class AssetCatalogSource implements CatalogSource {
  AssetCatalogSource({AssetBundle? bundle, String assetPath = _defaultAssetPath})
      : _bundle = bundle,
        _assetPath = assetPath;

  static const _defaultAssetPath = 'assets/data/exercise_catalog.json';

  // ...fields: _bundle, _assetPath, _loading, _byKey map...
  @override
  Future<void> ensureLoaded() => _loading ??= _load();

  Future<void> _load() async {
    try {
      final raw = await _assets.loadString(_assetPath);
      final list = (jsonDecode(raw) as List).cast<Map<String, dynamic>>();
      for (final e in list) {
        final info = ExerciseLaunchCatalogInfo(
          id: e['catalogId'] as String,
          isFormChecked: e['isFormChecked'] == true,
          vietnameseName: e['vietnameseName'] as String?,
          englishName: e['englishName'] as String?,
          classKey: e['classKey'] as String?,
          baseReps: (e['reps'] as num?)?.toInt(),
          baseSeconds: (e['seconds'] as num?)?.toInt(),
          baseSets: (e['sets'] as num?)?.toInt(),
        );
        // Index under EVERY alias so a lookup by catalog id OR definition id OR
        // class key resolves to the same entry — this is the id-mismatch fix
        // (e.g. catalog 'vup' and definition 'v__up' both land here).
        for (final alias in [
          e['catalogId'],
          e['definitionId'],
          e['classKey'],
        ]) {
          if (alias is String && alias.isNotEmpty) {
            _byKey[normalizeExerciseKey(alias)] = info;
          }
        }
      }
    } catch (error, stack) {
      // Leave the index empty; callers fall through to their never-crash floor.
    }
  }

🧒 Like you’re five

It reads the JSON once (_loading ??= _load() means “only start loading if I haven’t already”). For each exercise it makes a little info object, then files that same object in a lookup box under all three of its names. So later, whether the caller asks by "squat", "squat" or "squat" (here they happen to match, but for others like vup / v__up they don’t), it finds the row. If the file is missing or broken, it just leaves the box empty and nobody crashes — the launch code has a safe fallback.

  @override
  ExerciseLaunchCatalogInfo? lookup(String id) {
    final direct = _byKey[normalizeExerciseKey(id)];

🧠 Two id systems, one bridge

Notice lookup leans on lookupExerciseDefinition (section 05) as a second chance: if "pushups" isn’t a direct key, resolve it to the definition (push_up) first, then look up by that. So the catalog and the Dart registry cross-reference each other. Hold onto this — it’s the same alias table that section 04 uses, and it’s the fragile joint of the whole pipeline.

  /// Compact volume label for list/summary surfaces, e.g. "3 x 8 rep",
  /// "1 x 30 giây", or "3 x 2 x 30 giây" for repeated holds. Matches
  /// [workoutVolumeLabel]'s wording so cards and the exercise intro never
  /// disagree. Returns '' if the entry is malformed (neither target set).
  String get volumeLabel {
    final sets = baseSets ?? 1;
    if (baseSeconds != null) {
      final holdCount = baseReps;
      if (holdCount != null && holdCount > 1) {
        return '$sets x $holdCount x $baseSeconds giây';
      }
      return '$sets x $baseSeconds giây';
    }
    if (baseReps != null) return '$sets x $baseReps rep';
    return '';
  }
}

⚠️ A miss is invisible

If lookupExerciseDefinition(name) returns null — a typo’d exerciseName, or a card for an exercise not in the registry — the user taps and nothing happens. No error, no toast, only a debugPrint that’s stripped in release. Because the shelf cards (section 03) and the registry (section 05) are separate hand-maintained lists joined by this string, a dead card is easy to ship and hard to notice. Worth a guard/test that asserts every card’s exerciseName resolves.

ExerciseDefinition? lookupExerciseDefinition(String query) {
  final normalizedQuery = normalizeExerciseKey(_exerciseAlias(query));

  for (final definition in exerciseDefinitions) {
    if (normalizeExerciseKey(definition.id) == normalizedQuery ||
        normalizeExerciseKey(definition.name) == normalizedQuery) {
      return definition;
    }
  }

  return null;
}

String _exerciseAlias(String value) {
  return switch (normalizeExerciseKey(value)) {
    'airsquat' => 'squat',
    'squats' => 'squat',
    'squatbw' => 'squat',
    // ...dozens more: pushups→push_up, hipbridge→glute_bridge, etc...
    // Catalog-id -> Dart def-id bridges (resolve by ID, not display name).
    'butterfly' => 'butterfly__stretch',
    'tricepdip' => 'tricep__dip_(_floor)',
    'sideplankdip' => 'side__plank_with__hip__dip',
    'bowpose' => 'bow_',
    _ => value,
  };
}

String normalizeExerciseKey(String value) {
  return value.toLowerCase().replaceAll(RegExp(r'[^a-z0-9]+'), '');
}

💡 The alias table is a maintenance tax

Every id-spelling mismatch between the catalog, the plan engine, and the Dart registry is patched here by hand (look at those tricep__dip_(_floor) ids — clearly machine-generated). It works, but it’s the kind of table that silently rots: an exercise added with a new spelling won’t launch until someone remembers to add its alias. A stronger long-term fix is one canonical id everywhere; short term, a test that every catalog definitionId resolves via lookupExerciseDefinition.

  static ({int sets, int target, bool isHold}) _resolveVolume(
    ExerciseDefinition definition,
    VolumePrescription? prescription,
    ExerciseLaunchCatalogInfo? catalogInfo,
  ) {
    final catalogSeconds = catalogInfo?.baseSeconds;
    final catalogReps = catalogInfo?.baseReps;
    final rawSets =
        prescription?.sets ?? catalogInfo?.baseSets ?? kFallbackSets;
    // A plan may explicitly override the catalog modality. If neither source
    // is available (for example a direct library launch), the definition still
    // carries the modality so second-based exercises never fall back to reps.
    final isHold = prescription?.seconds != null
        ? true
        : prescription?.reps != null
            ? false
            : catalogSeconds != null
                ? true
                : catalogReps != null
                    ? false
                    : definition.targetType == ExerciseTargetType.seconds;
    final resolved = isHold
        ? (prescription?.seconds ?? catalogSeconds)
        : (prescription?.reps ?? catalogReps);
    final sets = rawSets < 1 ? 1 : rawSets;
    // Floor guards a missing or zero catalog target (a data error); the
    // displayed target / scoring denominator is never 0.
    final target = (resolved == null || resolved < 1)
        ? (isHold ? kFallbackSeconds : kFallbackReps)
        : resolved;
    assert(target > 0);
    // ...debug-warns if both catalogInfo and prescription are null...
    return (sets: sets, target: target, isHold: isHold);
  }

🧒 Like you’re five

Three jars of numbers, checked in order. Plan jar (prescription) first — if the coached plan said “8 reps,” use that. Else catalog jar — the default from the snapshot. Else the floor jar — a hardcoded safe number so nothing is ever zero (a zero target would divide the score by zero). It also decides reps vs hold: does this exercise count reps, or hold seconds? Same priority order, with the definition’s own targetType as the last tiebreak.

💡 This is the answer to “where do the reps come from?”

If a reviewer asks “why did my squat launch as 3×8?” — it’s this function. Not the card, not duration, not the Squat class. It’s prescription > catalog > floor, and for a plain library tap with a catalog row, it’s the catalog row: sets: 3, reps: 8 from the JSON in section 01.

  factory _ExerciseExperienceSpec.fromDefinition(
    ExerciseDefinition definition, {
    VolumePrescription? prescription,
    ExerciseLaunchCatalogInfo? catalogInfo,
  }) {
    // Resolve volume ONCE (prescription > catalog > floor). `target` is the
    // per-set goal AND the scoring denominator, so it is floored at 1.
    final resolvedCatalogInfo =
        catalogInfo ?? CatalogSource.instance.lookup(definition.id);
    final volume =
        _resolveVolume(definition, prescription, resolvedCatalogInfo);
    final sets = volume.sets;
    final target = volume.target;
    final isHold = volume.isHold;

    switch (definition.id) {
      // ...'squat_assessment', 'wall_pushup_assessment', ... each hardcoded...
      case 'squat':
        return _ExerciseExperienceSpec(
          sets: sets,
          repsPerSet: target,
          // ...badges, callouts, posture...
          createExercise: (repsPerSet) => Squat(maxRep: repsPerSet),  // ← hardcoded
        );
      default:
        // isHold comes from the DEFINITION's declared target type, not from
        // catalog seconds. Rep-type and hold-type both feed the single
        // resolved `target` into createExercise — never a null target.
        return _generic(
          definition: definition,
          sets: sets,
          repsPerSet: target,
          restSeconds: overrideRest,
          targetLabel: isHold ? 'GIÂY/HIỆP' : 'REP/HIỆP',
          secondsPerUnit: isHold ? 1 : 4,
          timeBased: isHold,
          createExercise: (targetPerSet) => definition.createExercise(   // ← uses the registry
            reps: isHold ? null : targetPerSet,
            seconds: isHold ? targetPerSet : null,
          ),
        );

⚠️ Two construction paths for the same class

For squat (and glute bridge, plank, the assessments…) there are now two places that build the exercise object: the registry’s createExercise: … Squat(maxRep: target) (section 05) and this screen’s hardcoded createExercise: (repsPerSet) => Squat(maxRep: repsPerSet). The library path goes through this switch, so the registry factory is dead code for those ids — but it still exists and other call-sites may use it. Edit one, forget the other, and they silently diverge. This is the single sharpest thing to review in the whole pipeline: is the duplication intentional (per-exercise intro UI needs the explicit case) or drift waiting to bite?

The gotchas, ranked by how much they’d bite

#WhatSev
1Dual factory paths. squat/glute_bridge/etc. are built by a hardcoded switch case that bypasses definition.createExercise. Editing one and not the other silently diverges. (§07b)review
2Snapshot can go stale. Editing the Supabase table without re-running generate_exercise_catalog.dart ships old numbers, silently. No runtime reconciliation on this path. (§01b)review
3Silent tap miss. An unregistered/typo’d exerciseName → debugPrint and a no-op tap. Shelf cards and registry are separate lists joined by a string. (§04)guard
4Fragile id join + alias table. Card→definition→catalog resolution rides a hand-maintained alias table with machine-generated ids. Rots quietly as exercises are added. (§04)test
5definition.duration is decorative. A '15 reps' String that never drives runtime. Easy to mistake for the real target. (§05a)doc
6Forgiving /exercise route. Accepts a bare ExerciseDefinition, so a call-site can launch with no catalog/prescription and still “work” via the floor. (§06c)note

🧠 The one-sentence summary

A library card is a string; that string resolves to a local recipe (definition); the recipe’s numbers come from an offline snapshot of a Supabase table; and the live exercise is minted by a factory that, for the common cases, the launch screen keeps its own hardcoded copy of. Three sources, one string joining them, and one duplication to keep honest.
