01 · Locked shape

What is already decided (do not re-open)

decisions.md 2026-07-10 "Setup/tracking-safety guidance moves to VOICE":

  • The pipeline-BLOCKING states speak: person-gate blocks (searching/paused), checkSafety (orientation, landmark-missing, lighting), the no-pose branch. Text-only was a silent dead system for a floor-bound user.

  • Firing is deterministic (principle 3): latch per class, fire-once-on-entry, silent while held, re-arm through an exit debounce, re-fire on genuine re-entry. NOT a probability draw.

  • Rev 2 — Nam's lavish review (07-10, 7 notes): a per-class MINIMUM RE-FIRE INTERVAL (~10s) [SUPERSEDED by Rev 3 — deleted]; implementation reuses the existing debouncer utilities; paused confirmed timer-free; resume = producer-emitted (adapter-edge rejected); UI copy defaults live in the UI table, signal carries only per-exercise overrides; searching-silent + missing-asset-no-op confirmed as designed.

Note the second line: side-view glute bridge passes safety with the far arm invisible. That is the whole reason the gate must stay granular — a literal full-body requirement would block this exercise forever, and a loosened one would score reps off landmarks it can't see (data honesty). The message says "be fully in frame" (simple, always-safe); the check only demands shoulder/hip/knee. That asymmetry is deliberate and must survive the refactor.

The seam is already half-built CueType.safety exists (voice_policy.dart, CueTuning(CueMode.always)), and policy_voice_coach.dart:128-131 holds a standing TODO(wiring): "ExerciseBase exposes no structured safety-event signal (only the generic resultIssues.feedback['System'] string shared by searching/paused/instruction copy). Wire CueType.safety once a real per-exercise hook exists." This design IS that hook. But CueMode.always returns true every frame — the latch/debounce below is the NEW logic deciding WHEN to hand it a key.

And the UI already sniffs strings — including a machine token smuggled INTO the display copy, which is the honest tell that the string channel is a de-facto enum with none of the type safety:

ELI5: the app already knows exactly which of a handful of situations you're in (turn sideways, step back, too dark, paused). But it only tells the pipeline by writing a Vietnamese sentence, then both the screen AND (soon) the voice have to READ that sentence back and guess which situation it meant. This design writes down the situation itself — a labelled tag — so the screen and the voice each just look up what to do. Same idea as an airport: the sign and the announcement both come from one departure code, not from someone re-reading the sign aloud.

03 · The backend

The producer emits a fine-grained class (so the UI keeps its rich glyph vocabulary), plus optional per-exercise copy. Voice collapses that class to a coarse content key (the anti-spam decision). 04 · The firing policy

The latch / debounce / slot state machine (read this hardest)

This is the CORE. It is deterministic — no probability, no hunger — because setup/structure/safety is reserved for causality (principle 3). The player (QueuedAssetVoicePlayer) stays a dumb FIFO; ALL of this lives in a new adapter-owned controller, sibling to VoicePolicy.

Per steady-state class (orientation, body_in_frame)

PSEUDOCODE — the per-class latch (feel-tune constants flagged; mirrors landed code)
state per class C:  CLEAR | LATCHED | LATCHED_RECUED
timers per class C: conditionTrueSince, conditionClearSince, latchedSince

each frame, given C's condition = present/absent this frame:

  CLEAR:
    if present for ≥ ENTER_DEBOUNCE_MS (~1s continuous):   // flicker guard
        request(C)              // enqueue into the single slot, latest-wins
        state = LATCHED; latchedSince = now
    // brief flicker to present-then-absent never crosses the debounce -> no fire
    // NOTE: request() enqueues into the slot; the PUMP is the ONLY gate
    // (sink-free + re-validation). No wall-clock re-fire block — a
    // debounced exit + genuine re-entry fires again.

  LATCHED:
    if absent for ≥ EXIT_DEBOUNCE_MS (~1s continuous):
        state = CLEAR           // re-armed; a genuine RE-ENTRY will fire again
    else if still present for ≥ RE_CUE_MS (~10s since latchedSince):
        request(C, recue=true)  // ONE re-cue, then quiet for real
        state = LATCHED_RECUED  // (fuller/help register is the content INTENT;
                                //  v1 audio replays the same file — missing-audio.md)

  LATCHED_RECUED:
    if absent for ≥ EXIT_DEBOUNCE_MS: state = CLEAR   // only exit is clearing
    // never fires again while continuously latched
Review directive — reuse the house debouncers The enter/exit timers are NOT new timer code: implement them with the existing utilities in lib/utils/ (StickyDebouncer / Debouncer — the same hysteresis machinery the orientation detector already trusts). One debouncer per class per edge, or one StickyDebouncer where its two-sided shape fits. New timer logic is limited to latchedSince bookkeeping (the RE_CUE_MS clock).

The single pending slot (latest-wins, re-validated at speak time)

Setup lines are state descriptions, not events. request(C) does NOT push straight to the FIFO — it writes ONE slot (overwriting any waiting request; latest wins). A pump drains the slot only when the sink is free — audio serialization is the ONLY drain gate (Rev 3: no time cooldowns). At drain time it re-validates: is C's condition still true right now?

  • Still true → speak (orientation → common.side_orientation, body_in_frame → common.body_in_frame).
  • Cleared while waiting → DROP silently. The drop is correct: the user already complied. Never FIFO-stack safety lines — a stale "turn sideways" after they already turned is worse than silence.
Rev 3 — no wall-clock re-fire block (the ~10s MIN_REFIRE was deleted) Rev 2 added a per-class ~10s minimum re-fire interval to kill cross-class ping-pong (phone-fiddling alternating orientation ↔ body every ~2s). Nam re-ruled after seeing it run: re-firing is governed ONLY by continuous-presence latch semantics — a debounced exit + genuine re-entry MUST fire again (fix orientation, regress 5s later → the coach responds). The failure mode of the floor (coach deaf to a real regression for up to 10s = feels dead) is worse than the noise it prevented, and fiddling is self-limiting. Anti-ping-pong is now the EXIT DEBOUNCE's job — instant flapping can't clear it, and its width is THE feel-tune knob if device tests show fiddle-spam (never a wall-clock block). Only one ~10s knob remains: RE_CUE_MS, the single "did you hear me" escalation while a class is CONTINUOUSLY latched — presence-based, dies on exit.

Edge classes (paused, resume)

  • paused fires once on the pause COMMIT edge — the gate's own person-lost grace IS its entire timing (confirmed in review). No enter-debounce, no cooldown logic of any kind on this class: the gate already decides when a pause is real, and stacking a second timer would double-delay the line. The latch controller treats the commit edge as pre-debounced.
  • resume — DECIDED in review: producer-emitted (a one-frame resume signal from the gate's resume edge), for one-family consistency — every guidance event flows through GuidanceSignal, so the UI and any future consumer see the same edge. The alternative (adapter detects the paused→active transition it already tracks for hustle gap-voiding) was REJECTED: it works, but splits guidance semantics across two layers. It is a one-shot, not a state; it does not latch.

Per-class grace at the SIGNAL layer (shared by UI + voice) — Rev 3

At exercise open the body/orientation conditions are trivially true (user isn't positioned yet), so a settle window suppresses the classes that ARE fixable in-position. Rev 3 made this per-class and moved it to the signal layer so BOTH renderers honour one clock — no renderer drift. Graced (ExerciseBase.kGuidanceSignalGraceClasses): bodyInFrame, lighting, turnSide, faceCamera. Ungraced (fire/show from frame one, because the user must fix them BEFORE getting into position, or they're informational/edge): phoneLandscape, phonePortrait, searching, paused, resume. The voice controller reads exercise.isGuidanceGraceActive(kind); the UI reads exercise.guidanceSignalForPresentation (null while a graced class is in grace) — one source of truth, so graced signage is suppressed on screen exactly when its voice is.

Grace anchor — fixed window from activation/set-start (pilot) The current PolicyVoiceCoach does NOT emit the setup intro (setup-voice wiring is parked; createVoiceCoach() returns PolicyVoiceCoach, and the legacy _speakSetup path in _GenericExerciseVoiceCoach is not on it). So there is no intro audio to anchor to; the pilot uses a fixed kGuidanceSignalGraceMs (3500ms, feel-tune) from set-start/activation. A clearly-commented seam re-anchors the grace to intro-audio-end when the parked setup cluster wires the intro (a Fable decision, next chat). No hard-coded intro-end dependency.
The integration point that will bite: the adapter early-returns policy_voice_coach.dart:133 — processFrame RETURNS early when state != activated || isPaused || !hasPose. Every setup/tracking-safety state hits that guard. The setup-safety controller MUST run BEFORE (or outside) that early-return — it is the one path that fires precisely when the rep pipeline is dormant. The controller reads exercise.guidanceSignal every frame regardless of exercise state. To be precise about scope (review note 4): this risk is voice-adapter-internal only. The UI signage path never goes through PolicyVoiceCoach and already renders guidance pre-activation; if the controller lands after the guard, the UI keeps working while the voice is silently dead — which is exactly what makes the bug easy to miss on device.

07 · Risks

Lines most likely wrong + what to stress-test

  • Flicker across class boundaries — the exit debounce is the guard (Rev 3). The two-edge debounce guards flicker WITHIN a class. Cross-class ping-pong (phone-fiddling alternating orientation-wrong ↔ body-out-of-frame every ~2s) was Rev 2's reason for a ~10s MIN_REFIRE, but Nam deleted that in Rev 3 (a wall-clock block also silenced genuine comply-then-regress). The guard is now the EXIT DEBOUNCE: instant flapping never clears it, so it never re-arms; its width is the feel-tune knob. Device watch item: if deliberate fiddling still produces annoying alternation, LENGTHEN the exit debounce — do not reintroduce a wall-clock block.
  • Intro grace vs a fast setter. A user who is already positioned when the set starts clears the frame before GRACE_MS ends. If they then drift out-of-frame right after grace, the first real block could feel late (it waits out the enter debounce on top). Tune GRACE_MS against real setup speed; err short — a slightly-early first cue beats a silent block. (Anchor itself is DECIDED: activation/set-start, §04.)
  • Pause-commit edge vs the enter debounce (double-debounce). The gate already applies a person-lost grace before it commits paused. If the latch ALSO runs its enter debounce on the paused class, the line lands ~1s+grace late. paused is an EDGE class — review-confirmed: NO extra timers of any kind on the pause path (no debounce, no cooldown). Verify one debounce, not two.
  • Stale-drop race (condition re-enters while a line is pending). Sequence: block fires → request enqueued → sink busy → user complies (condition clears) → user regresses (condition true again) BEFORE the pump drains. The slot still holds the original request; re-validation at drain sees "true" and speaks — correct outcome, but confirm the re-entry didn't also start a SECOND latch cycle that double-requests. The single-slot latest-wins collapses it to one; verify the latch state didn't go CLEAR→LATCHED twice across the comply/regress blip (the exit debounce should have swallowed the brief clear).
  • Adapter early-return (§04 warn). If the controller is placed after the existing guard it NEVER runs during the exact states it exists for. This is the most likely "it does nothing" bug. Stress-test: block the pipeline (turn the phone the wrong way) and confirm a line within ~1-2s.
  • Grace anchor drift (§04 tip). The anchor is DECIDED (activation/set-start), but the failure mode survives as an implementation risk: if Codex anchors to an intro-audio-end signal that doesn't exist yet, the grace never releases and the channel is silent forever. Test that a wrong-orientation open speaks after grace, not never.
  • The ~20-subclass checkSafety return-type change. Mechanical but wide; every subclass and its tests touch. flutter analyze + full test run gate it. The per-exercise granular logic must keep its exact semantics — only the return value changes shape.

Device stress-tests: (1) open wrong-oriented → line after grace, once, not machine-gunned; (2) comply → silence; regress (any time, even within a few s) → line again on debounced re-entry (Rev 3: no wall-clock block); (3) hold the block 15s → exactly one fuller re-cue at ~10s, then silence; (4) borderline confidence pose + deliberate phone-fiddling that alternates classes → the exit debounce should keep it from machine-gunning; if not, lengthen the exit debounce (NOT a wall-clock block); (5) walk out mid-set → paused on commit (not on first lost frame) → walk back → resume once → next rep counts; (6) pool-empty / key-missing → safe no-op, zero crashes (VoiceSink already no-ops unmapped keys); (7) glute side view with far arm invisible → still passes safety (the granular gate survived the refactor).

09 · Setup-instruction cluster

Intro / countdown / ready / set-complete + the stuck-user re-tell (ruled + landed late 07-10)

Ruling: decisions.md "Setup-instruction voice"; behavior spec § "Setup / structure". Implemented by an Opus subagent (Nam's explicit call), Fable-reviewed, on top of this doc's channel. Uncommitted, same review pass as the rest. Voice suite 86/86, exercise suite 135/135, analyze clean.

  • Intro = one-shot broadcast, NOT a latch. <slug>.setup_position + <slug>.active_intro fire back-to-back once at set start, unconditional — no pose/in-frame gating; the intro is what tells the user to get in frame. Latched per set (_introFired); a completed/activated → notActivated transition re-arms all per-set one-shots (inert for the single-set pilot, pre-wires multi-set).
  • Grace = VOICE-ONLY, spans exactly the intro playback (re-ruled latest 07-10). The window is re-pinned to now every frame while intro audio plays and CLOSES at intro-audio-end — no 3.5s settle tail (the ~1s enter debounce is the only residual delay). The UI is NOT gated: the guidance table renders the current signal live from frame one (a user still setting up is standing and reading the screen; it's the VOICE over the intro that was the double-speak). guidanceSignalForPresentation is removed. Intro-end detection waits on sink-idle with a generous 30s ceiling (the player's silent 4s default would fake "idle" mid-intro); if the intro produces no audio, voice grace falls back to the fixed ~3.5s set-start window. The 3.5s activation-edge re-anchor is retained (pre-dates these rulings).
  • The countdown TERMINATES a still-playing intro (ruled latest 07-10). A user already holding the start position has no use for setup instructions: the first count to fire while intro audio plays stops the sink (current + queued dropped), speaks immediately, and marks intro-audio-end at that moment — voice grace closes with it. The intro never resumes; it was consumed. The activation ring shows the remaining-seconds number CENTERED — the 'Giữ yên' caption is removed (Nam: it said nothing); the on-screen number stays count-down while the voice counts up, kept deliberately (mid-hold the user can't see the screen).
  • Voiced countdown "một / hai / ba" synced to the 3s hold at 800/1600/2400ms elapsed (feel-tune; 2400 < 3000 on purpose so "ba" fires before activation nulls the hold clock). Reuses the rep-count keys '1'/'2'/'3' → common/count_1..3.mp3, routed deterministically (never rep-count thinning). A broken hold drops pending counts (clearPending(), the currently-playing line finishes) and a re-hold restarts from "một"; activation keeps the queue so a mid-play "ba" survives as the go cue. holdStill itself stays lineless — the countdown owns that state's audio.
  • Stuck-user re-tell: setupPosition joins the latch controller with fireOnEntry: false — entry fire suppressed (the intro was the first telling); the ONE fire is a re-tell of setup_position when the class has been continuously latched and now − max(latch-start, intro-audio-end) ≥ ~10s (own constant, separate knob from RE_CUE_MS). Null intro-end blocks it outright — it can never speak over the intro. Debounced exit + re-entry re-arms exactly one more.
  • common.ready once on the activation edge; common.set_complete once on completion — differs from legacy, which spoke exercise_complete. Needs Nam's listen-check (§ stress-test list).
