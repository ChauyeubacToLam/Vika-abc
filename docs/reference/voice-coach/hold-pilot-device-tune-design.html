Fix 1 · Voice policy

A milestone always speaks an outcome — never silent

Concept + why

Inside a hold, when the clock crosses a milestone (halfway, final-10s) the coach speaks the time line and then an encouragement — praise if the hold has been clean, hustle if it has been struggling or is in the final stretch. On device, "Được một nửa rồi" landed in silence and felt dead. Nam wants an encouragement every mark. The ruling (decisions.md #1): the time line must be followed deterministically by praise OR hustle — no probability miss, no silent slot — while keeping the clean→praise / struggling-or-final→hustle switch and never-praise-twice-in-a-row.

Where the probabilities live, and the two ways today's slot goes silent

The time line is CueType.count, which is already deterministic — the fleet default is base: 1.0, personality-immune, short-circuiting the roll (voice_policy.dart:128, _count at :445). So the number always speaks; the bug is purely the follow-up. The praise/hustle odds live in kDefaultTuning (praise at :134, hustle at :175) and are rolled in _praise/_hustle via _rollWithReason. Two independent silent paths exist:

lib/voice/policy_voice_coach.dart · _maybeFireHoldMilestone · L623-647 (current)
final sinkBusyBeforeCount = _coach.isBusy;
_coach.say(CueType.count, VoiceContent.key(key),
    CueContext(repNumber: repNumber, contentKey: id));   // time line — deterministic, always fires

final isFinalStretch = threshold >= target * (2 / 3);
var praised = false;
if (!_cleanSinceLastHoldMilestone || isFinalStretch) {
  _coach.say(CueType.hustle, VoiceContent.pool(script.hustlePool),
      CueContext(repNumber: repNumber, sinkBusy: sinkBusyBeforeCount));   // (A) rolled → can MISS
} else if (!_lastHoldMilestoneWasPraise) {
  praised = _coach.say(CueType.praise, VoiceContent.pool(script.praisePool),
      CueContext(repNumber: repNumber, clean: true, formScore: 1.0));     // (A) rolled → can MISS
}                                                                          // (B) clean & last-was-praise → NEITHER branch → SILENT
_lastHoldMilestoneWasPraise = praised;
_cleanSinceLastHoldMilestone = true;
  • (A) Roll miss. Both say() calls go through _policy.decide and roll (praise-roll p≈0.50, hustle-roll p≈0.50). A miss = silence.
  • (B) Suppressed branch. When the hold is clean (→ praise branch) but the last milestone was already praise, the else if (!_lastHoldMilestoneWasPraise) is false → nothing runs after the time line.
  • (C, hidden) Second milestone in one hold. Praise/hustle are outcome cues. The first milestone's praise sets _outcomesThisRep = 1 for this hold's repNumber; the second milestone then trips _canStartOutcome's 'second-outcome-slot-is-critical-only' (voice_policy.dart:377) and is dropped even if the roll would hit. Another silent path the ruling kills.

Proposed change (Codex writes the Dart)

Two pieces: a deterministic force so the follow-up can't miss or be gated, and a call-site precedence that resolves the switch + never-twice into a single guaranteed emit.

1. A hold-milestone-only force flag. Add final bool force (default false) to CueContext (voice_content.dart:63, add to the ctor and copyWith). In _praise and _hustle, add as the first line:

if (ctx.force) { lastReason = '<type>-forced'; return true; }

Placed first, it bypasses the roll, the never-twice check, _canStartOutcome (so the 2nd-milestone (C) path fires), and the hustle perishable sinkBusy drop — a true guarantee. decide() still calls _onSpoke afterward, so hunger/outcome bookkeeping stays consistent. Rep exercises never pass force, so their odds are untouched — this is the requirement "do NOT change rep-path praise/hustle odds."

2. Call-site precedence in _maybeFireHoldMilestone. Resolve the choice before emitting, then emit once, forced:

policy_voice_coach.dart · replaces L630-646 (described, not final Dart)
final isFinalStretch = threshold >= target * (2 / 3);
// switch: struggling OR final stretch → hustle; else praise
var wantHustle = !_cleanSinceLastHoldMilestone || isFinalStretch;
// never-praise-twice: a clean mark whose predecessor already praised → hustle
if (!wantHustle && _lastHoldMilestoneWasPraise) wantHustle = true;

if (wantHustle) {
  _coach.say(CueType.hustle, VoiceContent.pool(script.hustlePool),
      CueContext(repNumber: repNumber, force: true, sinkBusy: sinkBusyBeforeCount));
} else {
  _coach.say(CueType.praise, VoiceContent.pool(script.praisePool),
      CueContext(repNumber: repNumber, clean: true, formScore: 1.0, force: true));
}
_lastHoldMilestoneWasPraise = !wantHustle;
_cleanSinceLastHoldMilestone = true;
Answering the precedence question Clean-but-last-was-praise → hustle (the never-twice bump). Because the branch is forced, there is no roll to miss and no second branch to fall through to — the "fall through to the other" the ruling describes collapses into this one bump (praise→hustle). Hustle has no never-twice rule and is forced, so it always lands. Determinism proven: exactly one of the two always fires.
Lines most likely wrong / to stress-test
  • Force bypassing _canStartOutcome entirely is the boldest interpretation. It means a forced milestone can start even mid-collision-gap. For a hold that's fine (the count line plays, the forced line queues after — the sink plays sequentially), but confirm on device the two lines don't clip. If Nam wants the collision gap respected, move the force check to after _canStartOutcome — but then path (C) resurfaces. I chose full bypass to honor "no silent slot"; flag for review.
  • A forced praise still writes _lastPraiseRep via _onSpoke. Harmless (we track never-twice at the call site via _lastHoldMilestoneWasPraise, not the policy's _lastPraiseRep), but note it so a reviewer isn't surprised the two mechanisms coexist.
  • Stress-test: a long hold with two milestones — confirm both speak a follow-up (kills path C); a clean hold across two consecutive holds — confirm no praise-twice; a struggling hold — confirm hustle every mark.

Fix 2 · CV — designed hardest CORE

Outer-ring horizontality gate: a standing user must drop the hold

Concept + why

The outer anti-cheat ring gates the clock on four angle terms — body (shoulder-hip-ankle), arm, knee, and hip-sag. The failure: a person standing or walking around has all four ~180°/low-sag too. shoulder-hip-ankle is straight when you stand; arms and knees are straight; there is no sag. Geometrically a standing body is indistinguishable from a plank on these terms, so no threshold value catches "walked around" — Nam's "tighten the threshold" instinct cannot work. The missing signal is torso orientation: a plank torso is horizontal, a standing torso is vertical. Add that as another outer-ring exit term.

Verify the claim in code

high_plank.dart · _updateStateMachine · L520-546 (current outer ring)
final isInsideOuterEntry =
    bodyAngle >= OUTER_ENTRY_BODY_MIN &&   // 115°  — straight when STANDING too
    armAngle  >= OUTER_ENTRY_ARM_MIN  &&   // 100°  — straight when standing too
    kneeAngle >= OUTER_ENTRY_KNEE_MIN &&   // 100°  — straight when standing too
    hipDev    <  OUTER_ENTRY_SAG_MAX;      // 0.38  — no sag when standing
final isOutsideOuterRing =
    bodyAngle < OUTER_EXIT_BODY_MIN ||   // 105°
    armAngle  < OUTER_EXIT_ARM_MIN  ||   // 90°
    kneeAngle < OUTER_EXIT_KNEE_MIN ||   // 90°
    hipDev    >= OUTER_EXIT_SAG_MAX;     // 0.45  — none of these fire when you stand up

bodyAngle = calculateAngleNormalized(shoulder, hip, ankle) (high_plank.dart:441) — a joint angle, invariant to whole-body rotation. Rotating a straight body from horizontal to vertical does not change it. Confirmed: standing never trips the ring.

The geometry of the new term

Torso vector = shoulder → hip (the ruling's landmarks; more robust than shoulder→ankle because the ankle is the noisiest/most-occludable point and the trunk is the most direct lying-down-vs-upright signal). Measure its angle from horizontal in image space:

dx = |shoulder.x − hip.x| (horizontal extent of the torso) dy = |shoulder.y − hip.y| (vertical extent; image Y is DOWN) torsoTiltDeg = atan2(dy, dx) · 180/π PLANK ┌─ shoulder ──────── hip ─┐ dx ≫ dy → torsoTiltDeg ≈ 0–25° (horizontal) STAND shoulder dx ≈ 0 │ dy ≫ dx → torsoTiltDeg ≈ 70–90° (vertical) hip

Why this form is robust for a side-on landscape exercise:

  • Scale-invariant. atan2(dy,dx) is a pure ratio — body size and scaleFactor are irrelevant, so no normalization needed and no cross-body drift.
  • Camera-facing-invariant. landscapeLeft vs landscapeRight flips the X sign; the abs() on both deltas cancels it. No cameraFacing branch.
  • Already proven in this file. The START gate uses the identical idea — isHorizontal = dx > dy * 1.2 on shoulder→ankle (high_plank.dart:296-300) — and start detection works on device. That validates the coordinate convention (Y down, torso genuinely dx≫dy in a plank) empirically. We're lifting the same proven pattern into the outer ring, on the torso segment, expressed as an angle for a clean threshold.
high_plank.dart · reused START-gate precedent · L296-300
// Cơ thể nằm ngang (khoảng cách X lớn hơn Y)
double dx = (shoulder.x - ankle.x).abs();
double dy = (shoulder.y - ankle.y).abs();
bool isHorizontal = dx > dy * 1.2;   // ← same principle, START only, not in the ring

Thresholds + hysteresis, and how it composes

Add two config constants and fold the term into the existing entry/exit booleans. The existing frame hysteresis (4-frame _holdingDebouncer on entry, 2-frame _droppingDebouncer on exit) is untouched; the entry/exit value split gives the angular hysteresis band:

ConstantValueMeaning
OUTER_ENTRY_TORSO_TILT_MAX40°To (re)enter the hold the torso must be within 40° of horizontal (AND into isInsideOuterEntry).
OUTER_EXIT_TORSO_TILT_MAX55°Torso beyond 55° of horizontal drops the hold (OR into isOutsideOuterRing).

Compute torsoTiltDeg in checkingPose alongside the other angles (high_plank.dart:441-446), pass it into _updateStateMachine as a new param, and add:

isInsideOuterEntry  = ...existing... && torsoTiltDeg <= OUTER_ENTRY_TORSO_TILT_MAX;
isOutsideOuterRing  = ...existing... || torsoTiltDeg >  OUTER_EXIT_TORSO_TILT_MAX;

Adding to both entry and exit is deliberate: a standing user can neither start nor continue a hold. The entry term also correctly gates re-arm (which reuses confirmedOuterPose, see Fix 3) — you cannot re-arm the hold while standing.

Why 40/55 tolerates the worst legal plank

The widest a legal plank's torso tilts is a deep sag or a high pike. A sag at the outer-ring limit is hipDev ≈ 0.45 of a torso length in Y; over a torso that's atan(0.45) ≈ 24°. A pike is symmetric. So worst legal ≈ 24–30°, comfortably under the 40° entry. Standing is 70–90°, far past the 55° exit. The 15° band between 40 and 55 (plus the frame debouncers) absorbs jitter without flip-flop.

Assumptions most likely wrong — the CORE risk list
  • #1 (riskiest): the sag→tilt coupling. I assumed a legal deep sag keeps the shoulder→hip torso near-horizontal. But sag drops the HIP; if the shoulders also drop or the hip landmark is read low, the torso segment itself could tilt more than my 24° estimate. If a real sagging plank tilts past 40° the user would be wrongly ejected. Stress-test the sag case first and hardest; if the torso tilts more than expected, raise ENTRY to ~45–50° (there's a huge 20°+ margin to standing, so loosening is safe). Do NOT go the other way and tighten toward standing.
  • #2 landmark noise on a short segment. shoulder→hip is shorter than shoulder→ankle, so atan2 jitters more per pixel of landmark noise. Mitigations already in place: One-Euro smoothing upstream, the confidence gate (isLandmarkConfident on all six landmarks, high_plank.dart:291-294,420-425), and the 4/2-frame debouncers. If it still jitters near the band, widen the band, don't add new smoothing.
  • #3 side-lying flat. Lying on your side has a horizontal torso → this term will NOT drop it. That's expected and correct: the orientation gate only targets vertical torsos. Side-lying is caught by _hasFloorSupport / arm-vertical-lift, not here. Don't try to make one term do both.
  • #4 which landmarks in the pair. ML Kit gives left+right shoulder/hip; the existing code already resolves a single shoulder/hip via _getLandmarks (the camera-facing-nearer side). Reuse those exact resolved landmarks — do not re-pick.
On-device stress matrix Standing still in frame (must drop) · walking across frame (must drop) · kneeling upright, torso vertical (must drop) · deep legal sag (must NOT drop — assumption #1) · high pike (must NOT drop) · side-lying flat (will NOT drop — expected) · partial/occluded lower body (confidence gate handles) · standing→plank transition (re-arm must re-enter cleanly). Log torsoTiltDeg in the existing diagnostic dump (high_plank.dart:392-396) so the band can be tuned from real numbers.
Fences held This touches ONLY the outer ring in high_plank.dart + two new HighPlankConfig constants. It does not read or change the inner-ring form metrics (sagging/piked/elbow/timer), the START gate, or any other exercise.

Fix 3 · State machine + UI

Re-arm reproduces the set-start "get into position" behavior

Concept + why

Not a new feature and not a new line — reuse set-start's setup_position machinery whole, UI and its voice. The re-arm between holds must behave exactly like the very start: once the user is in frame + correctly oriented but not yet in the pose, the existing "get into position" UI + its voice fire (set-start's stuck-user behavior); if the user is already posed at re-arm, straight to "ba, hai, một" — no get-into-position prompt. Two impl regressions break that reproduction.

Constraint REVERSED (Nam, supersedes the round-2 voice-silent ruling) The earlier "re-arm stays voice-silent" ruling is gone (decisions.md "High Plank device-tune" #3/#4 supersede it). Nam: "utilize what we already have — the UI that says get into position and the voice that goes with it; don't introduce anything else; just make that UI and voice work correctly after a break." The elegance is that the setup_position voice is a delayed stuck-user re-tell, so it fires only when the user actually needs the prompt — never on a clean per-hold re-arm, so no spam. That anti-spam property is why reusing set-start's machinery is the right answer rather than a new line or an immediate re-tell.

Bug (a): rest freezes when the user leaves the frame

The resting → reArming transition lives inside _updateStateMachine, which runs only inside checkingPose → processPose → and only when a pose is present. There is no pose-independent tick: the page picks processPose OR processNoPoseFrame per frame (confirmed in exercise_base.dart; the two are mutually exclusive, chosen at active_exercise_page.dart:1191-1198 and :1497-1504). So if the user walks off during rest, only processNoPoseFrame runs — and High Plank's override does nothing to the rest clock:

high_plank.dart · L350-355 (current no-pose override) + L547-551 (rest advance)
Map<String, String> processNoPoseFrame() {
  _interruptActiveHold('wall_guard');   // no-op unless holding
  _interruptReArm();                    // no-op unless reArming
  return super.processNoPoseFrame();    // gate + guidance only — never advances _restStartMs
}
// the ONLY place rest completes — pose-gated, unreachable when the user is absent:
} else if (state == HighPlankState.resting && _restStartMs != null) {
  final restSeconds = (now - _restStartMs!) / 1000.0;
  if (restSeconds >= HighPlankConfig.REST_DURATION_SECONDS) {
    _transitionState(HighPlankState.reArming, now);
  }
}

Result: leave the frame during rest → machine stuck in resting, ring frozen at 0.

Fix (a): drive rest completion on a pose-independent time check. In the processNoPoseFrame override, after super.processNoPoseFrame() (which refreshes frameTimestamp via DateTime.now() and publishes the correct absent-user guidance), run the same resting→reArming wall-clock check the state machine uses. Extract it into a tiny shared helper — e.g. _advanceRestOnClock(int now) — called from both the resting branch of _updateStateMachine and the no-pose override, so there is one rest-completion rule. Because rest is a pure timer keyed off _restStartMs and wall-clock frameTimestampMs, it counts down correctly whether or not a pose is present. When it completes to reArming while the user is still away, the base's guidance (searching / body-in-frame) keeps telling them to get back in frame — which is exactly what set-start does when you're absent.

Interaction to verify — the presence-gate pause When a person is lost for long enough, the base's presence gate (_gate.onNoPose) may declare a pause and demand a re-hold on return (_beginPauseReactivationIfNeeded). That overlaps with our rest→reArming advance — both converge on "get back into position," so they're probably compatible, but this is the one place two state owners meet. Stress-test: leave the frame mid-rest for 3s, 10s, 30s and confirm the machine lands in a clean reArming (or pause-reactivation) that then plays 3-2-1 once — not a double countdown or a wedged state. If they fight, gate the rest-advance on "not paused" and let the pause flow own the long-absence case.

Bug (b): guidance hides the re-arm "get into position"

The pre-fix re-arm get-into-position was a bespoke drained ring label gated by guidanceCopy == null. The current code deletes that unreachable label call and routes the posed 3-2-1 through the live RestCountdownRing:

active_exercise_page.dart · L2188-2213 (current re-arm ring)
if (widget.isTimeBased && activeState &&
    guidanceCopy == null &&                 // ← ANY guidance line hides the re-arm ring
    !(isReArming && reArmProgress != null))
  Center(child: AnimatedSwitcher( ...
    child: holdRestRemaining != null || isReArming
        ? RestCountdownRing(
            remainingSeconds: reArmCounting
                ? total * (1 - reArmProgress)
                : holdRestRemaining ?? 0,
            totalSeconds: reArmCounting ? total : _restRingTotalSeconds)
        : HoldHeroRing(...)));

Guidance now owns the not-posed stage; once pose confirmation starts, lineless hold guidance exposes this ring and the countdown. Transient body-in-frame or side-orientation guidance therefore cannot leave a dead "Vào tư thế" ring competing for the center.

How set-start actually does it (the machinery to mirror). Set-start does not use a bespoke ring. It publishes a single GuidanceSignal through one priority slot:

mis-oriented → gate blocks, publishes turnSide, processPose early-returns (banner: "Đứng nghiêng") in-frame, not posed → checkExerciseState publishes GuidanceSignal.setupPosition (banner: "Vào vị trí") in position, holding → publishes holdStill (maps to guidanceCopy == null) → _CenterOverlay 3-2-1 ring 3s held → activated / hold begins

The priority is automatic: a single guidanceSignal slot, cleared every frame, and a bad orientation early-returns before checkExerciseState ever publishes setupPosition (exercise_base.dart:540-542 vs :561). So turnSide naturally wins over setupPosition, and setupPosition only appears when framing/orientation are already good.

Fix (b) — reuse that machinery instead of the bespoke ring, voice included. During reArming, when the user is not yet in the pose (the re-arm hold hasn't started — activationProgress == null / _reArmHoldStartMs == null), publish GuidanceSignal.setupPosition('Vào vị trí', 'Vào tư thế và giữ yên để bắt đầu.') from High Plank's own path (right after _updateStateMachine in checkingPose) — the same signal, same copy as set-start's exercise_base.dart:878-883. Once the user is posed and the re-arm hold-still starts, publish GuidanceSignal.holdStill(...) (copy maps to null) — again mirroring set-start's sequence. Then everything else already works:

  • UI. The existing set-start UI renders both identically: _currentGuidanceCopy maps setupPosition → the "Vào vị trí" banner (active_exercise_page.dart:2550) and holdStill → null (:2557), so once posed the existing _CenterOverlay hold branch renders the 3-2-1 (it already maps re-arm-with-progress to _LiveOverlayState.hold, :2473-2475). No new widget. The bespoke centerLabel: 'Vào tư thế' ring becomes dead code (setupPosition makes guidanceCopy non-null, so its guidanceCopy == null guard hides it) — flag it, don't delete unless Nam confirms.
  • Voice — this is the part that just falls out. The setup-voice producer (_SetupSafetyVoiceController.processFrame) is signal-driven, not state-scoped: activeClass = _classForSignal(exercise.guidanceSignal) (policy_voice_coach.dart:1287-1288), and it runs every frame including during a hold set. So the instant the guidance signal is setupPosition, its stuck-user re-tell latch is live at re-arm too — no change to the voice machinery at all. The re-tell is delayed (_recueMs = 10s, :1219, floored at intro-audio-end which is already stamped from set-start), so a clean per-hold re-arm (user posed within the delay → signal clears) stays silent, and only a genuinely stuck user hears "Vào vị trí." That IS the anti-spam property Nam wants, for free.
  • Already posed → straight to countdown. The activation countdown (_handleActivationCountdown) is already reArming-aware — inActivationContext = notActivated || isReArmingHold (:439-441) — so "ba, hai, một" fires at re-arm with no change. A user already posed publishes no setupPosition signal, so no get-into-position voice; they go straight to the count. Exactly set-start's behavior.
  • Priority for free. Mis-oriented / partial-body → the gate blocks and processPose early-returns before checkingPose (exercise_base.dart:540-542), so setupPosition is never published that frame — the orientation banner shows, exactly as at set-start.
Does the setup_position producer widen cleanly? YES — this is the answer to the "same machinery" test The voice producer needs no widening: it already keys off the guidance signal, so it is reachable from the activated/reArming state the moment the signal is present. The only code change is High Plank re-emitting the same GuidanceSignal.setupPosition/holdStill from its reArming path — which touches neither checkExerciseState nor the base setup machinery, so set-start behavior is unchanged. The intro voice (_fireSetupIntro) stays latched to set-start (isSetStart) — we deliberately do NOT re-fire it, because the immediate first-tell would spam every re-arm; the delayed re-tell is the right voice.
