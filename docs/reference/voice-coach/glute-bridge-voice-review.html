What glute bridge said on this review branch

Before any code: here is the net behaviour once you strip away the machinery. This is what you would hear if you did a glute-bridge set on device right now, on this branch.

Count ✅ works“Một… Hai… Ba…” — the landed rep number, stochastically thinned by the policy. This path is correct and tested.
Praise ⚠ fires too freely“Tốt lắm!” on clean reps — good. But it also fires on bad-form reps (~1 in 5), because corrections get mis-filtered into the praise branch. Data-honesty leak.
Correction 🔴 never firesNot once, for any glute-bridge fault. The fault ids the rep logs and the fault ids the voice script expects don’t match, so every fault is dropped.
Hustle ⛔ offThe finish-line “Cố lên!” never fires — the base factory doesn’t pass a rep target, so the policy can’t tell it’s the final reps.
Phase ⛔ noneGlute bridge ships no phase cues (only squat wired those), so no “Nâng hông / Giữ / Hạ xuống” voice.
Setup / safety / set-complete ⛔ unwiredThe adapter never emits instruction or safety cues at all, for any exercise yet. All the on-screen setup coaching stays silent.

🔴 The one that matters

Glute bridge’s per-rep fault types are PascalCase metric names (HipExtension, SpeedControl, KneeAngle, NeckHead, Hyperextension). The voice script’s faultIds are snake_case (hip_extension, speed, knee_angle, neck, lumbar). The new adapter matches them with a plain contains — zero overlap → no corrections, and faulty reps fall through to praise. The old coach had a normalization layer that bridged this; the migration dropped it. Full breakdown in §06.

02 Orientation

The cast — five new files, one seam

The whole feature is a clean pipeline: an adapter turns per-frame camera state into discrete “cue requests”, a brain decides whether each one speaks, a façade picks the exact words, and a sink makes the sound. Data lives apart from logic. Here is who owns what.

FileRoleOwnsPure?
voice_content.dartData layer CueType, CueContext, VoiceLib (the line catalog), VoiceScript (per-exercise footprint)Yes — no I/O
voice_policy.dartThe brain Whether a cue speaks: hunger, hard rules, relief valves. Deterministic given an injected Random+clockYes — no I/O
voice_coach.dartThe façade What to say: pool pick with no immediate repeat, the D8 praiseBig bias Almost — fires at the sink
voice_sink.dartThe sound Logical key → asset path (the swappable VoiceSet seam), plays the clip, safe no-op on missing audioNo — the only audio I/O
policy_voice_coach.dartThe adapter The whole reason the camera pipeline is untouched: it diffs frame-to-frame state and turns rep-landings / faults / phase-changes into cue requestsNo — holds prior-frame state

🧒 ELI5

Think of a real PT. The adapter is the PT’s eyes — it notices “a rep just finished, and the hips didn’t come up high enough.” The brain is the PT’s judgement — “do I say something this rep, or let it slide and watch?” The façade is word choice — “Tốt” vs “Tốt lắm!”. The sink is the mouth. Splitting them means you can make the PT chattier, or swap their voice, without touching the eyes.

✔ Verdict — the architecture is genuinely good

This separation is the strongest part of the work. The brain is pure and unit-tested to the behaviour (not the numbers), the data is a flat catalog, and the adapter honours the “zero pipeline changes” guardrail (decision D1). My findings below are almost all about the seam between this new system and the existing exercise code — not the system’s own design.

03 The path

One glute-bridge rep, end to end

Here is the exact journey of a single completed rep from the state machine to a sound. Rows in red are where the chain breaks for glute bridge specifically.

GluteBridge._onRepCompleted()
Descent hits bottom → repCount += 1, metrics evaluated, and a RepLog is written with fault_types: [...] — the PascalCase metric names.
active_exercise_page._processVoiceFrame()
Every frame calls coach.processFrame(exercise, repCount, hasPose, feedback). The coach is a PolicyVoiceCoach built by the base factory.
PolicyVoiceCoach.processFrame()
Sees repCount went up → _handleRepLanded(). Reads the latest RepLog, extracts fault ids.
_faultIdsFor() — THE BREAK
Filters fault_types against script.faultIds with a plain contains. PascalCase vs snake_case → always empty. Every fault vanishes here.
say(count) ✅  /  say(praise) ⚠
Because faults are empty, the rep looks clean: count fires (good), and the praise branch runs — even on a bad rep. Correction’s say() is never called.
VoicePolicy.decide()
The brain rolls the dice for count/praise. Works perfectly — it just never receives a correct request to reason about.
VoiceCoach._resolveKey() → AssetVoiceSink.playKey()
Pick a variation, resolve the logical key to an mp3, play it. Missing audio = silent no-op (never throws).

04 The seam

The wiring — how glute bridge gets its coach

Glute bridge does not override createVoiceCoach(). So it inherits the base factory. This is the single most important block for the review, because every glue decision for glute bridge is made here — and two of them are wrong or incomplete.

lib/exercise/exercise_base.dart — the inherited factoryL369–387
ExerciseVoiceCoach? createVoiceCoach() {
  // Keep the same per-exercise footprint the legacy generic coach used:
  // both script types map fault ids to '<slug>.<id>' asset keys.
  final legacy =
      GenericExerciseVoiceAssets.scriptForExerciseName(exerciseName);
  final bundle = liveHoldTargetSeconds != null
      ? VoiceDefaults.timeBased
      : VoiceDefaults.repBased;
  final script = VoiceScript.from(
    bundle,
    slug: legacy.slug,
    faultIds: legacy.faultIds,          // <- ['hip_extension','lumbar','knee_angle','neck','speed']
  );
  return PolicyVoiceCoach(
    script: script,
    coach: VoiceCoach(sink: AssetVoiceSink()),
    // no targetReps: passed  -> hustle can never fire
    countsByRepNumber: liveHoldTargetSeconds == null,   // true for glute bridge
  );
}

🧒 ELI5

“When the exercise page opens, build a talking coach. Reuse the exercise’s existing footprint (its slug and its list of fault names) from the old lookup table. If it’s a timed hold, use time-based counting; otherwise count reps. Then hand that to the new policy coach.” For glute bridge: liveHoldTargetSeconds is null → rep-based, counts by rep number. Confirmed by the wiring test.

⚠ Verdict — two problems seeded right here

(1) The faultIds are the wrong vocabulary. legacy.faultIds for “Glute Bridge” is ['hip_extension', 'lumbar', 'knee_angle', 'neck', 'speed'] — but those never match what the rep log actually records (see §06). The comment claims “keep the same footprint,” but the old coach normalized before comparing; copying just the id list without the normalizer is what breaks it.

(2) targetReps is never passed. Only squat’s override passes it. Glute bridge knows its maxRep, but the base factory has no access to it (there’s no maxRep on ExerciseBase). So isFinalReps is always false and the hustle cue is dead for every generic exercise. Defensible as staging, but worth a decision: thread a rep target through, or accept “no finish-line push” for non-squat exercises.

Compare squat’s override, which is the “fully wired” reference. It adds exactly the two things the base omits — phaseCues and targetReps:

lib/exercise/squat/squat.dart — the stage-3 pilot, for contrastL214–239

💡 Note the asymmetry

Squat is a hand-tuned override; glute bridge rides the generic base. That’s fine if the generic base is correct — but the base is where the faultId mismatch and the missing rep-target both live. Fixing the base fixes every generic rep exercise at once (bird dog, push up, lunge, curl-up…), which is a much higher-leverage fix than patching glute bridge alone.

05 The adapter

PolicyVoiceCoach — diff the frame, emit the cues

This is the class that lets the camera pipeline stay untouched. It implements the exact old ExerciseVoiceCoach interface and holds prior-frame state so it can tell “a rep just landed” from “same frame as before.” First, the per-frame entry point:

lib/voice/policy_voice_coach.dart — processFrameL72–109
@override
void processFrame({
  required ExerciseBase exercise,
  required int repCount,
  required bool hasPose,
  required Map<String, String> feedback,   // <- never read (see verdict)
}) {
  final state = exercise.exerciseState;
  final justActivated = state == ExerciseState.activated &&
      _lastExerciseState != ExerciseState.activated;
  if (justActivated || !_hasBegunSet) {
    _coach.beginSet();                 // wipe hunger + diff state
    _faultFirstSeenRep.clear();
    _lastPhaseCue = null;
    _hasBegunSet = true;
  }
  _lastExerciseState = state;

  // TODO(wiring): ExerciseBase exposes no structured safety-event signal ...

  if (state != ExerciseState.activated || exercise.isPaused || !hasPose) {
    _lastRepCount = repCount;
    return;
  }

  final repIncreased = repCount > _lastRepCount;
  if (repIncreased) {
    _handleRepLanded(exercise: exercise, repCount: repCount);
  }
  _maybeSpeakPhaseCue(exercise: exercise, repCount: repCount);
  _lastRepCount = repCount;
}

🧒 ELI5

“Every frame: if we just started a set, reset everything. If we’re not actively exercising, do nothing. If the rep counter ticked up since last frame, react to that finished rep. Then maybe say a movement cue.” The clever bit is repIncreased — it turns a per-frame stream into discrete “a rep happened” events without the exercise having to fire callbacks.

✔ Verdict — the diff loop is solid

Activation-edge detection (justActivated), the paused/no-pose guard, and updating _lastRepCount on every return path (so a paused rep doesn’t double-count on resume) are all correct. For glute bridge, _maybeSpeakPhaseCue is a no-op because the script has no phaseCues — so this reduces to “react to landed reps.”

Now the heart of it — what happens when a rep lands. I’ve trimmed to the decision logic:

lib/voice/policy_voice_coach.dart — _handleRepLanded (trimmed)L111–187
void _handleRepLanded({required ExerciseBase exercise, required int repCount}) {
  final repLog = _latestRepLog(exercise, repCount);
  final faultIds = _faultIdsFor(repLog);     // <- returns [] for glute bridge, always
  final clean = faultIds.isEmpty;                // <- so 'clean' is ALWAYS true
  final isFinalReps = _isFinalReps(repCount);    // <- always false (no targetReps)

  final formScore = (repLog?.correctForm ?? true) ? 1.0 : 0.0;

  final baseCtx = CueContext(
    repNumber: repCount, isFinalReps: isFinalReps,
    clean: clean, formScore: formScore,
  );

  final countContent = countsByRepNumber
      ? VoiceContent.key(repCount.toString())     // glute bridge: speak the rep number
      : VoiceContent.pool(script.countPool);
  _coach.say(CueType.count, countContent, baseCtx);   // ✅ this works

  if (faultIds.isNotEmpty) {                     // <- NEVER entered for glute bridge
    for (final id in faultIds) {
      final firstSeenRep = _faultFirstSeenRep.putIfAbsent(id, () => repCount);
      final persistence = repCount - firstSeenRep;
      _coach.say(CueType.correct,
          VoiceContent.key(script.faultKey(id)),
          baseCtx.copyWith(contentKey: id, faultPersistence: persistence));
    }
    _faultFirstSeenRep.removeWhere((id, _) => !faultIds.contains(id));
  } else {                                       // <- ALWAYS taken, even on bad reps
    _faultFirstSeenRep.clear();
    _coach.say(CueType.praise, VoiceContent.pool(script.praisePool), baseCtx);
  }

  if (isFinalReps) {                             // <- never true for glute bridge
    _coach.say(CueType.hustle, VoiceContent.pool(script.hustlePool), baseCtx);
  }
}

🧒 ELI5

“A rep landed. Figure out its faults. Always try a count. If there are faults, say a correction for each; otherwise say a praise. If it’s a finish-line rep, try a hustle.” The whole thing hinges on one line: faultIds = _faultIdsFor(repLog). If that returns an empty list, the exercise looks flawless to the coach — count + praise, no correction, ever.

⚠ Verdict — the design here is right; the input to it is poisoned

The logic is exactly what the spec asks for: count, then one outcome (correct-or-praise), then maybe hustle. The persistence tracking via _faultFirstSeenRep is also correct — it resets when a fault disappears, so faultPersistence is a true consecutive-streak count. But because _faultIdsFor returns empty for glute bridge, this whole block collapses to “count + praise,” and the else praise branch runs on genuinely bad reps. The formScore = ... ? 1.0 : 0.0 line is the only thing partially masking it — see the next section for why that’s a fragile safety net, not a fix.

⚠ Your catch (note on the fault loop) — the voiced correction isn’t chosen by priority

“So we say all the corrections? I think it should be the most important one → most severe.” Right instinct, and half-handled: it does not say all. The loop calls say(correct) once per fault, but the policy’s one-outcome-cue-per-rep guard means the first fault that wins its dice roll speaks and the rest are blocked — so it’s ≤1 correction per rep. But which one wins is iteration-order + dice, not priority. fault_types is a bare allFaults.map((f) => f.type).toSet().toList(), so FaultRecord.priority is thrown away before it ever reaches the coach. The metrics have priority — glute bridge already sorts by it for the on-screen topFault — the voice path just can’t see it. So the spec’s “only the highest-priority one speaks” is unmet. Fix it together with F1: when you rewrite the RepLog fault list, emit it priority-sorted (or log priority next to type) and have the adapter voice only the first entry. Logged as F1b.

💡 Quick clarify (note on the isFinalReps block)

“So the praise is only for the last rep?” No — praise fires on any clean rep (the else branch a few lines up). The if (isFinalReps) block is a separate, additional cue: the finish-line hustle (“Cố lên!”), which for glute bridge never runs anyway (no targetReps — F2). So: praise = every clean rep; hustle = only the final rep or two, and only once a rep target is wired in.

06 The critical finding

🔴 The fault-id mismatch — corrections can’t fire

This is the finding to read twice. It’s a single-line filter with a vocabulary mismatch on either side of it, and it silently kills the entire correction feature for glute bridge (and, I suspect, most generic exercises).

✅ Decided (2026-07-08) — “what is this list doing? if it’s only to recheck the replog, remove it”

Confirmed, and yes — remove it. I grepped every read of .faultIds (the list) in lib/: in the new system it’s read in exactly one place, the _faultIdsFor gate below (policy_voice_coach.dart:218). The audio key is built by faultKey(id) from the individual id off the replog (voice_content.dart:269) — it never consults the list. As a gate it’s pure redundancy, and it’s the exact line that kills every glute-bridge correction today. Drop it; use whatever the replog carries. (The two other reads are inside the old _GenericExerciseVoiceCoach, which stage 5 deletes.)

One coupling, don’t miss it: “use whatever’s in the replog” only produces the right audio key because you’re also renaming the metric types to snake_case (your option-A call, §06). Raw replog + no rename → faultKey spits out glute_bridge.HipExtension, still no matching asset. The two changes are one change: rename the four metric types to snake_case and delete the filter — together they make corrections fire with the correct keys.

One job not to lose: in the old coach the list’s order was the priority — script.faultIds.firstWhere(detected.contains) (exercise_base.dart:911) spoke the earliest-declared fault, so if hip and neck both faulted it said the hip. If you just speak raw replog order you drop that (F1b). Clean replacement: sort the replog faults by FaultRecord.priority (metrics already carry it; glute bridge already uses it for the on-screen topFault) and speak only the first — which also answers your other note “say the most important one, not all.” One move retires the filter and restores priority.

The filter that assumes they’re the same vocabulary

lib/voice/policy_voice_coach.dart — _faultIdsForL210–223
List<String> _faultIdsFor(RepLog? repLog) {
  if (repLog == null || repLog.correctForm) return const [];  // warnings-only reps exit here
  final raw = repLog.data['fault_types'];
  if (raw is! Iterable) return const [];
  final ids = <String>[];
  for (final item in raw) {
    final id = item.toString().trim();          // 'HipExtension' — NOT normalized
    if (id.isEmpty) continue;
    if (script.faultIds.isEmpty || script.faultIds.contains(id)) {  // contains('HipExtension') == false
      ids.add(id);
    }
  }
  return ids;                                     // -> [] for every glute-bridge fault
}

🔴 Finding F1 — the exact failure, step by step

Given: a rep with a hard hip-extension fault → correctForm == false, fault_types == ['HipExtension'].

Then: _faultIdsFor passes the first guard (not correctForm), reads 'HipExtension', checks ['hip_extension',…].contains('HipExtension') → false → returns [].

So back in _handleRepLanded: faultIds.isEmpty → the else branch runs → say(CueType.praise, …) on a bad-form rep. Correction’s say() is never reached. formScore is 0.0 (because correctForm is false), which damps the praise roll to ~0.6× and blocks praiseBig — so it’s a muted “Tốt,” roughly a 1-in-5 chance, not a gushing “Xuất sắc!”. But it is still praise on a rep the system flagged as wrong. That violates the data-honesty guardrail and hard-rule #10 (“every cue backed by a measurement”).

Net for glute bridge: corrections never fire; a fraction of bad reps get quietly praised; all four form metrics are voice-invisible.

Why it worked before — the normalizer the migration dropped

The old _GenericExerciseVoiceCoach didn’t compare raw strings. It ran each fault type through a normalization + candidate-id layer that mapped free text to snake_case ids:

lib/exercise/exercise_base.dart — the OLD coach’s bridge (still present, now unused for this)L982–995
Iterable<String> _faultIdsForText(GenericExerciseVoiceScript script, String text) sync* {
  final normalizedKey = _normalizeFaultKey(text);
  for (final candidate in _candidateFaultIdsForKey(normalizedKey)) {
    if (script.hasFault(candidate)) yield candidate;     // 'knee' -> 'knee_angle' ✓
  }
  final normalizedText = _normalizeFaultText(text);
  for (final candidate in _candidateFaultIds(normalizedText)) {
    if (script.hasFault(candidate)) yield candidate;     // 'speed' -> 'speed' ✓, 'neck' -> 'neck' ✓
  }
}

💡 What that normalizer actually resolved for glute bridge

I traced _candidateFaultIds for the four metric names. It would have matched: HipExtension → hip_extension (the text.contains('hip') branch yields hip_extension), KneeAngle → knee_angle, SpeedControl → speed (the tempo/speed branch), NeckHead → neck. That’s 4 of 5 ids bridged. (Hyperextension was the one likely gap even in the old path.) The new adapter bridges zero. This is a clean regression, not a pre-existing bug — the correction feature demonstrably worked for glute bridge before and doesn’t now.

✅ Decided with Nam — 2026-07-08 (live notes)

Your question, anchored on faultIds: “what else are we using these fault ids for? if it’s just for checking then it’s redundant — just use whatever’s in the replog.” Verified — you’re right. So as a filter it is redundant: drop it and let whatever the RepLog carries flow straight to the audio key. (Its only side job — hiding faults with no recorded audio — is already covered downstream by the sink’s safe no-op, §09.)

For completeness, the three options I’d have weighed — before you called it:

  • A — one vocabulary at the source. Make the metrics emit snake_case type strings that equal the voice faultIds. Cleanest long-term (single source of truth), but f.type is also used as the on-screen feedback key (resultIssues.feedback[topFault.type]) and the setFeedback map key, so it’s not a voice-only change.
  • B — carry an explicit map in VoiceScript. A {typeString → faultId} table per exercise. Localises the change to the voice layer, no ripple, but it’s another thing to keep in sync per exercise.

Your call: option A — snake_case everywhere (your convention). Rename the four metrics’ type strings to hip_extension / hyperextension / knee_angle / speed_control / neck_head so they equal the audio keys, and delete the faultIds filter (or leave it empty) so the RepLog ids flow through untouched. Scoped to glute bridge only for now — it’s the test exercise; the rest of the fleet waits (your note on §04). One thing to eyeball while renaming type: it’s also the on-screen feedback key (resultIssues.feedback[topFault.type]) and the setFeedback history key, so glance at anything reading those literal strings before you flip them — but by your convention they should be snake_case too, so it’s consistency, not risk.

07 The brain

VoicePolicy — where “not predictive” is actually built

Even though glute bridge only exercises the count and praise paths today, the brain is worth reviewing because it’s what shapes every cue once F1 is fixed. It’s pure and deterministic given an injected Random. Three pieces matter most: the hunger formula, the count cap story, and the relief valves.

lib/voice/voice_policy.dart — the hunger formula & the count ruleL237–280
// scale: (base + step·idle) · personality, clamped by cap.
double _p(CueTuning t, int idle) =>
    _clampD((t.base + t.step * idle) * personality, 0.0, t.cap);

bool _count(CueContext ctx) {
  if (ctx.repNumber <= 1) return true;      // Rep 1 always fires — the anchor.
  final t = tuning[CueType.count]!;
  final idle = _idle[_key(CueType.count, ctx)] ?? 0;
  if (idle >= t.reliefAfter) {              // 6 straight silent counts
    return true;                          // uncounted-set guard, consumes no roll
  }
  return _rng.nextDouble() < _p(t, idle);   // middle reps: ~70%, +15/skip, capped 0.90
}

🧒 ELI5

“Hunger” = how many times in a row this cue could have spoken but didn’t. The longer the silence, the higher the odds next time — so the coach never goes weirdly quiet, but it’s never on a fixed timer either. Rep 1 always counts (proof the counter works). Middle reps are a real coin-flip that gets more likely the longer you’ve gone silent, but it’s capped below certainty so you can never learn “it went quiet twice, so the next one always counts.”

✔ Verdict — the count cap story is the best-defended code in the feature

The cap: 0.90 (not 1.0) and the reliefAfter: 6 both have inline comments tying them to your 2026-07-08 call that “caps/floors are saturation guards, not schedulers.” The test roll saturates below certainty pins exactly the bug you heard on device (the alternating even-number rhythm). This matches the humanlike-cadence-is-stochastic memory precisely. No change needed — just confirming the intent survived into code.

The praise path carries the D8 “praise ∝ quality” logic — the piece that interacts with glute bridge’s poisoned formScore:

lib/voice/voice_policy.dart — _praise (D8 scaling)L282–300
bool _praise(CueContext ctx) {
  if (_lastPraiseRep == ctx.repNumber - 1) return false;  // never twice in a row
  if (_lastOutcomeRep == ctx.repNumber) return false;     // one outcome cue per rep
  final t = tuning[CueType.praise]!;
  final idle = _idle[_key(CueType.praise, ctx)] ?? 0;
  final roll = _p(t, idle);
  final formScore = _clampD(ctx.formScore, 0.0, 1.0);
  final scaled = _clampD(roll * (0.6 + 0.4 * formScore), 0.0, t.cap);
  return _rng.nextDouble() < scaled;
}

⚠ Verdict — this is the only thing standing between F1 and a real embarrassment

On a bad glute-bridge rep, formScore is 0.0, so scaled = roll * 0.6 — praise is damped but not silenced (by design: even a so-so rep should occasionally get a “nice”). That means the F1 bug doesn’t praise every bad rep, only ~60% as often as a clean one. It’s a coincidental cushion, not a guard. Once F1 is fixed, bad reps take the correction branch and never reach _praise at all, so this cushion stops mattering — which is the right end state. Don’t “fix” F1 by hardening this; fix the fault vocabulary.

08 Intent review

Where the code and the behaviour spec disagree

Code review asks “does it do what it says.” Intent review asks “does what it says match what we decided.” I read the behaviour spec against the policy. One real divergence, one coupling worth a conscious decision.

Spec hard-rule #5 says “first fault is always cued.” The code rolls 25%. divergence

The behaviour spec (principle 3: “deterministic is reserved for causality”) lists as a hard rule: “First occurrence of a fault-id in a set: always cue it (deterministic — causal response).” But _correct has no first-occurrence branch:

lib/voice/voice_policy.dart — _correctL302–313
bool _correct(CueContext ctx) {
  if (_lastOutcomeRep == ctx.repNumber) return false;   // one outcome cue per rep
  final t = tuning[CueType.correct]!;
  if (ctx.faultPersistence >= t.reliefAfter) {           // relief valve at persistence 4
    return true;
  }
  return _rng.nextDouble() < _p(t, ctx.faultPersistence);  // persistence 0 -> base 0.25
}

⚠ Finding — first fault has a 75% chance of silence, not 0%

On first sighting, the adapter passes faultPersistence: 0, so _p = the base 0.25. That means the first time you break form, the coach stays quiet 3 times out of 4 — the opposite of the spec’s “react to something the user just did, always.” The implementation-guide’s §4 quietly replaced “first always” with “25→55→85 by persistence,” and the code followed the guide, not the spec. Someone (you) needs to decide which is canon: is the causal first-reaction a locked principle, or did that soften on purpose? If it’s locked, _correct needs a faultPersistence == 0 → return true line (respecting the one-outcome-per-rep guard).

affectsForm does double duty — safety-ish cues can’t speak coupling

Your note — “should [it] gate on correctForm?” It already does, and that gate is exactly the coupling worth a conscious call. _faultIdsFor exits early on repLog.correctForm. And correctForm = !allFaults.any((f) => f.affectsForm). So a rep whose only fault is affectsForm: false — e.g. NeckHead (cervical strain, an injury cue) or a speed/knee warning — is treated as fully clean, exits before any correction is considered, and gets the praise branch.

💡 Verdict — probably fine, but make it a conscious choice

This aligns with the spec’s bandwidth principle (“minor wobble inside tolerance = silence”), so it’s defensible. But note the consequence: even after F1 is fixed, NeckHead will never be voiced, because it never flips correctForm. If “đặt đầu xuống sàn” is something you want spoken (it’s injury-adjacent, though not acute safety), then affectsForm is the wrong gate for voice eligibility — voice should key off “is there a fault with audio,” not “did the rep score as good form.” Two different questions currently answered by one flag.

09 Words & sound

Content resolution and the sink

Two short blocks to close the loop: how the façade picks the exact words, and how the sink turns a logical key into a sound (and fails safe when the audio isn’t recorded yet).

lib/voice/voice_coach.dart — _resolveKey (pool pick + praiseBig bias)L61–97
String? _resolveKey(CueType type, VoiceContent content, CueContext ctx) {
  var pool = content.keys;
  if (pool.length == 1) {                          // a single key with registered variations
    final variations = VoiceLib.variations[pool.first];
    if (variations != null && variations.isNotEmpty) pool = variations;
  }
  if (type == CueType.praise &&
      ctx.formScore >= _praiseBigFormScoreThreshold &&   // 0.85
      VoiceLib.praiseBig.isNotEmpty &&
      _rng.nextDouble() < _praiseBigBias) {              // 50%
    pool = VoiceLib.praiseBig;                          // "Xuất sắc!" on standout reps
  }
  // ... pick at random, avoiding the immediately-previous key for this pool ...
}

🧒 ELI5

“If the caller gave one key that has a family of phrasings, treat it as the family. If this is a praise on a really clean rep, flip a coin to upgrade ‘Tốt’ → ‘Tốt lắm!’. Then pick a line, but not the same one you just said.” The no-immediate-repeat is per-pool, so counts and praises don’t interfere.

✔ Verdict — correct, and the glute-bridge tie-in

Because glute-bridge praise only ever fires with formScore either 1.0 (clean) or 0.0 (the F1-mislabeled bad reps), the praiseBig upgrade only triggers on genuinely clean reps — so at least the gushing praise is honest even with F1 present. Small mercy.

lib/voice/voice_sink.dart — AssetVoiceSink.playKey (safe no-op)L105–136
@override
Future<void> playKey(String logicalKey) async {
  final resolved = voiceSet.resolve(logicalKey);
  if (resolved == null) {                    // no asset recorded for this key
    debugPrint('[VoiceSink:...] no asset mapped for "$logicalKey" — skipping');
    _missingKeys.add(logicalKey);              // live missing-audio checklist
    return;                                   // never throws
  }
  _busy = true;
  unawaited(_player.waitUntilIdle(timeout: const Duration(seconds: 30)).then((_) {
    _busy = false;
  }));
  await _player.speak(logicalKey);
}

💡 Verdict — the no-op is load-bearing, and it hides F1 from crashing but not from failing

The safe no-op is why the app ships green while audio is incomplete — good. But it also means F1 produces no error, no crash, no log noise you’d notice — corrections just silently never happen. If you want an early-warning tripwire, missingKeysSeen is already tracked; surfacing it in debug mode (or asserting it’s empty in an integration test) would have caught F1 the moment a fault fired with an unmapped key. One caveat on _busy: overlapping playKey calls each register their own waitUntilIdle callback, so isBusy reflects “the player is idle,” not “my specific clip finished” — fine for the perishable-cue gate it feeds, just don’t lean on it for precise sequencing.

10 Loose ends

Dead flags & silently-lost intent

Two smaller things specific to glute bridge that a reader would miss unless they cross-referenced the old coach.

Glute bridge’s thoughtful “don’t replay stale faults” override is now dead code lost intent

⚠ Verdict — the flag is real intent, but nothing reads it anymore

shouldReplayPreviousSetVoiceFaults is only consulted by the old _GenericExerciseVoiceCoach._speakPreviousSetAdviceIfNeeded. PolicyVoiceCoach never reads it. So this override is a no-op today. The net effect is “correct by accident” (the new coach doesn’t replay anything, which is what this wanted), but the intent — “on the floor, don’t let last set’s faults leak into this one’s setup” — is now unenforced and will silently not apply if/when advice-replay gets wired into the new coach. Worth a // TODO or a test so the intent isn’t lost when stage-3/4 lands.

Cues defined but never emitted by the adapter unwired

CueType.instruction and CueType.safety exist in the enum and have full policy bodies, but PolicyVoiceCoach never calls say() with either. So the spec’s deterministic structure (setup intro, ready, rest, set-complete, no-count help; hard-rules #1, #2, #9) and all safety voice are unimplemented in the new path. The squat override’s comment says this is deliberate staging (“leaving setup/complete silent until the later instruction wiring stage”). Fair — but for glute bridge today it means the rich on-screen setup coaching (KneeAngle, NeckHead, HipExtension instructions) is entirely voice-silent, where the old generic coach spoke a setup intro and replayed prior-set advice. It’s the single biggest behavioural delta of the migration; just naming it so it’s a known gap, not a surprise.
