Next-rep instruction: correct mid-rep, remind at the next attempt

The voice twin of the UI's addInstruction layer. A continuous critical fault cued real-time in rep N earns one short feedforward reminder at the moment the user commits to rep N+1 — then the coach goes quiet and watches. 01 · Locked shape

What is already decided (do not re-open)

decisions.md 2026-07-09 "Next-rep instruction layer" + the LOCKED stub in voice-behavior-spec.md:

  • A continuous critical fault (live-emitted, affectsForm: true) that occurred in rep N earns a ≤7-word feedforward reminder at rep N+1's commit edge — the state-machine transition out of rest into the rep's first movement phase. Glute: bottom→ascending and the descending→ascending fast-path.
  • Peak faults excluded — their rep-end line already IS next-rep guidance.
  • Outcome-class cue: collision gap, cap-2/rep, blocked ≠ spent, carries the fault's contentKey. Reminder outranks hustle when both arm at one moment.
  • Rep-start and hustle's effort-phase entry are two declared moments that coincide on glute and share plumbing there; squat would separate them.
  • Same-content consecutive-rep ban (Nam device ruling 07-12, hard rule 12; landed same day): a reminder for fault X spoken into rep N is never followed by the same X into rep N+1 — the adapter skips the banned id in the priority pick (_highestPriorityReminderFaultId), so selection falls through to the next eligible fault, or silence if none. A DIFFERENT fault back-to-back is fine. Ban expires after one reminder-free rep (rep-number arithmetic, only reminders that actually SPOKE count) and resets per set.
  • Confirm-after-fix: deferred. Numbers: open, feel-tune. Research: voice-research-rules.md §3b.

03 · The moment

Detecting the commit edge — no new plumbing class

The adapter already reads exercise.currentPhaseKey every frame to fire phase cues (policy_voice_coach.dart:333-343, _maybeSpeakPhaseCue). The commit edge is one new observation on the same signal: the phase key transitions into a declared rep-start key from any non-rep-start key.

declaration — mirrors hustle's VoiceScript.effortPhaseKeys precedent (07-09 review Q4)
// VoiceScript (lib/voice/voice_content.dart) — content layer owns phase semantics
final Set<String> repStartPhaseKeys;   // glute_bridge: {'ascending'}
// hustle already declares: effortPhaseKeys // glute_bridge: {'ascending'} — same set, SHARED edge
// squat later: repStartPhaseKeys {'descending'}, effortPhaseKeys {'ascending'} — moments separate

One adapter-level edge detector (previous frame's key vs this frame's) emits "rep attempt started". Both the reminder and hustle consume that event where their declared sets match the entered key. On glute the two sets are identical, so it is literally one edge feeding two cues; on squat they diverge with zero rework. This is the "share plumbing where they coincide, stay two declared moments" call from decisions.md.

Why the fast-path matters glute_bridge.dart's descending state can exit straight into ascending (_onRepCompleted → transition(ascending)) — no bottom at all. On that path rep-land (count + rep N's outcome cues) and the commit edge land on the same instant. The adapter processes rep-land first; by the time the reminder rolls, _outcomeAudioPending / the collision gap usually block it → it drops. That is CORRECT behavior, not a bug: one moment, one outcome (principle 4). The reminder is perishable at its edge; its eligibility survives to the next edge (blocked ≠ spent).

04 · Eligibility & cadence

When it may speak, and how often it does

Eligibility (deterministic, adapter-owned)

  • Fault was detected in rep N (the immediately previous rep) — detected means the live critical was SEEN (_seenFaultTypesThisRep), whether or not its real-time line actually voiced (a gap-blocked correction still earns the reminder; blocked ≠ spent).
  • Fault is a live-emitted critical (affectsForm == true) with a mapped reminder line.
  • Fault absent in rep N → hard stop, no draw at all. Silence owns solved problems (§3b: don't narrate a fixed fault). This is the auto-taper — no explicit decay schedule needed.
  • Max 1 reminder per rep, always the set's highest-priority eligible fault (_faultPriorityFor order, same as corrections).

Cadence (probabilistic, policy-owned) — reuses the correction machinery wholesale

The reminder's shape IS CueMode.correction: first-of-streak deterministic, then an escalating roll, per-fault hunger key. No new policy mechanism — a new CueType.reminder dispatching to the existing _criticalFault-style body with its own tuning row:

proposed tuning (glute pilot) — ALL numbers feel-tune, flagged for Nam
CueType.reminder: CueTuning(
  CueMode.correction,
  base: 0.30,   // later reminder in a persisting fault streak: quiet-ish
  step: 0.15,   // climbs while the fault keeps recurring un-reminded
  cap:  0.65,   // BELOW criticalFault's 0.85 — the mid-rep re-correction still exists;
                // the reminder is the follow-through, not the main channel
  firstOccurrenceCertain: true,  // streak's FIRST reminder always fires (principle 3:
)                                // it's the causal follow-through of the correction)

ctx.faultPersistence carries the reminder streak (how many commit edges this uninterrupted fault-run has already been reminded at), exactly parallel to how corrections pass persistence today. Personality scales it like everything else; hard rules stay immune.

Expected feel (10-rep set, hyperextension on reps 3-6): mid-rep correction rep 3 (first occurrence, 100%) → reminder at rep 4's raise ("lần này siết bụng…", streak-first, 100%) → rep 5 raise: roll 30%, likely silent — mid-rep escalation may re-cue instead → rep 6 raise: roll 45% → rep 7 clean → silence, forever, until the fault returns. Never two fault lines at one moment; never the same fault twice within a rep (the contentKey rule blocks it for free).

Slotting

  • Outcome-class: registers in _canStartOutcome, subject to collision gap + cap-2.
  • Never the second in-rep slot (that stays criticalFault-only, unchanged).
  • At the commit edge its only rival is hustle → reminder checks first; if it speaks, hustle's own _canStartOutcome blocks on pending audio. Implements "reminder outranks hustle" with zero new priority machinery.
  • Phase cues at the same edge: unchanged — they are perishable non-outcome and drop if the sink is busy; check reminder before the phase cue so the outcome wins the breath.

07 · Risks

Lines most likely wrong + what to stress-test

  • Streak-first deterministic (the 100%) is my strongest assumption. It reads as principle-3 causality to me, but it is also the difference between "coach follows through" and "coach always nags twice per new fault" (mid-rep line + next-raise line ≈ 4-6s apart). If device feel says naggy, the one-line fix is firstOccurrenceCertain: false, base ~0.6. Nam decides on device.
  • Cap 0.65 vs the mid-rep escalation running in parallel. Both channels track the same fault; worst case alternates correction/reminder/correction across reps. The collision gap and same-fault in-rep block bound it, but the combined per-fault talk rate is untested — watch total lines per persisting fault across a 10-rep set (should be ≲4).
  • Edge detection vs debouncers. _ascendDebouncer delays the ascending transition a few frames; the reminder therefore starts slightly INTO the raise. Fine for hyperextension (a bottom/lower-phase fault — the cue still precedes it). Wrong only if a future exercise has a fault in the first ~300ms of its first phase; note it in the fleet rollout checklist, ignore for the pilot.
  • Fast-path starvation. A user who never pauses at bottom may have most reminders gap-blocked by rep-land audio. Acceptable (their reps are continuous, the mid-rep channel still corrects), but verify on device that SOME reminders land at real tempo — if ~none do, revisit priorities at the coincident moment, don't lengthen the gap.
  • NEW (post-review) — the neck_head flip is a scoring change, not just a voice change. With affectsForm: true, a lifted head makes the rep not-clean: praise dries up for head-lifters, form scores drop, and the fault fires real-time as a deterministic-first criticalFault using the EXISTING 4.4s neck_head.mp3 — the longest line in the set, now on the most reliable trigger. Works, but consider a shorter re-record soon. The pending neck_head_soft recording goes on hold (soft path unreachable after the flip).
  • NEW (post-review) — the addInstruction deletion sweep is fleet-wide. ~13 files across six exercises plus the UI consumer (active_exercise_page.dart) and the base mechanism. Mechanical, but it crosses exercise lanes (curl_up etc.) — analyze + full test run gate it, and the removed VN strings should be captured in the owning exercises' voice line references before deletion.

Device stress-tests: (1) continuous-tempo 10-rep set with forced hyperextension every rep — count total voiced lines for the fault, check ≤~4 and never two in one breath; (2) rest-at-bottom set — reminder must land right as the raise starts, not during the rest; (3) fault on final rep — no reminder after set-complete (no commit edge exists; verify no stray fire); (4) fix-after-reminder — rep goes clean → verify total silence about the fault from then on; (5) pool-empty wiring (stage A) — zero audible change vs today.
