00 · How to use this

What the diff does, and where to look

Four runs landed on top of each other in one working tree. Run 1 (structural): High Plank goes from a single form-gated hold-timer to maxHolds × holdSeconds reps-of-holds; the clock splits into an outer anti-cheat ring (gates time) and an inner form ring (coaches, never stops the clock); the spoken "năm…một" countdown and a new EarconPlayer end tone replace the spoken set-complete fleet-wide; the legacy bespoke coach is deleted. Run 2 (re-arm + hybrid): adds holding → resting → reArming → holding, a rest-end tone, typed rest getters, and the hybrid rings-plus-rep-hero UI. Run 3 (device tune): forces one praise/hustle after every milestone, adds shoulder→hip torso tilt to the outer ring, advances rest without a pose, and republishes set-start setup/hold signals during re-arm. Run 4 (pre-scale safety): discards a partial hold across the base pause ritual, gates timer deltas, validates the temporary hold phase/pool contract, logs measured clamped hold time, and removes dead generic voice/UI paths.

Read core first

The state machine (§03) and the voice adapter (§04) carry the algorithmic risk. The earcon/sink/factory/UI sections are glue — skim for pattern-match, not correctness.

02 · Review calls

Two implementation choices + one device-tune ruling

The first two are Codex choices the earlier spec left open or asked it not to reshape. The third is settled behavior whose ~10s feel still needs the phone.

① Hybrid modality = orthogonal booleans, not the ExerciseModality enum bless

Spec said
Addendum R4: "Introduce a modality on the page spec — ExerciseModality { reps, time, hybrid } (or two booleans if the enum over-reaches; report)."
Code does
No enum. Keeps isTimeBased and adds a nullable showRepTracking on ActiveExercisePage (showsRepTracking => showRepTracking ?? !isTimeBased), plus a hybrid bool + repHeroTarget on _ExerciseExperienceSpec. High Plank sets timeBased:true, hybrid:true, repHeroTarget:holdCount. Rings gate on isTimeBased; rep hero gates on showsRepTracking.
Why
The two render gates were already two independent booleans (:2157 rep hero vs :2185 rings). An enum would have to be decoded back into exactly these two booleans at both sites; the flags express "show rings" and "show rep tracking" as the orthogonal axes they actually are, and the default (?? !isTimeBased) keeps every existing exercise byte-identical.
Verdict: bless the two-flag shape, or require the enum for a single named source of truth? Cost of flags: "hybrid" is implied by timeBased && showsRepTracking rather than stated once.

② Intro-termination made structurally notActivated-only bless

Spec said
Addendum R2 item 2: "Do NOT touch the intro-termination branch — with no ritual instruction, _introFired can never be true during re-arm… confirm rather than modify."
Code does
Modified it. Two guards added: the grace-open block now excludes resting/reArming (:236), and the intro-termination inside _handleActivationCountdown now requires exerciseState == notActivated before it can _coach.stop() (:456). A new wiring test asserts this ("intro termination stays set-start-only").
Why
"Can never be true" was true by data flow but not enforced structurally. Widening the countdown gate to fire during re-arm made the intro-termination branch reachable in the re-arm context on paper; Codex chose a structural guard over trusting the invariant. Defensible — it converts a reasoning-only guarantee into a compiled one.
Verdict: accept the belt-and-suspenders guard (a modification the spec said not to make), or insist on the confirm-only path to keep set-start code untouched? The guard changes set-start-reachable code, so first-activation behavior needs a regression read (the wiring test covers "ready fires once; termination set-start-only").

③ Re-arm setup voice reuses the signal-driven stuck-user path device check

Ruling
The device-tune decision supersedes the earlier voice-silent addendum: re-arm must reuse set-start's setup_position behavior whole, UI and voice, without replaying the per-set intro.
Code does
High Plank republishes the exact GuidanceSignal.setupPosition copy while re-arming out of pose and holdStill once its private re-arm clock starts. The existing signal-driven _SetupSafetyVoiceController handles the line: entry stays silent, a continuous stuck state speaks once after its existing ~10s delay, and a clean/already-posed re-arm goes straight to "ba, hai, một." Base checkExerciseState and the voice controller are unchanged.
Why
One producer, two existing renderers. The UI gets the set-start banner immediately; the already-trained delayed latch prevents per-hold voice spam. Re-arm is still ungraced because the grace-open block excludes resting/reArming.
Device verdict: is the existing ~10s delay right after a break? Unit coverage proves fast re-arm silence, a real absent→present latch reset, and one stuck-user re-tell, but only the phone can settle the feel.

When the base starts pause reactivation, High Plank returns its internal state to setup, discards the current partial hold, and requires a fresh hold from zero. Completed reps/logs and completed-hold time survive.
