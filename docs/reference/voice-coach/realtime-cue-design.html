01 The ask

Goal & what's already locked

Make critical and soft form faults fire in real time — the instant the metric detects them, mid-rep — superseding today's fire-everything-at-rep-completion. This is the 07-08 decision (state.md: "correct + soft fire REAL-TIME off the mid-rep signal, superseding rep-completion timing"), scoped to glute bridge.

Locked · timingCritical fault = fires immediately, always (first occurrence certain). This IS "safety fires immediately" — there is no separate injury cue.
Locked · softSoft fault = fires in real time too, but probabilistic: hunger + base (not deterministic, not first-occurrence-certain).
UnchangedCount + praise stay post-rep (only knowable at rep-end: the rep number, and "clean = no fault all rep"). Rename to criticalFault / softFault / setup is done + green.

This doc designs only the real-time core. The two mechanical stages that ship alongside it — final-2-reps-always-counted, and the setup/ready/complete voice layer — go straight into the Codex prompt; they need no design review.

02 Current state

How critical/soft fire today — batched, at rep-completion

The adapter reacts only when repCount increments. It reads the just-written RepLog, classifies the whole rep, and speaks one outcome cue. Accurate, but a full rep late.

lib/voice/policy_voice_coach.dart — _handleRepLanded (today)the 3-way branch
// fires only on repCount++, off RepLog.data['fault_types'] + correctForm
if (correctionIds.isNotEmpty) {          // !correctForm -> a critical fault
  for (final id in correctionIds)
    _coach.say(CueType.criticalFault, VoiceContent.key(script.faultKey(id)), ctx…);
} else if (usesSoftClassifier && faultIds.isNotEmpty) {  // correctForm but minor faults
  for (final id in faultIds)
    _coach.say(CueType.softFault, VoiceContent.pool(script.softPoolFor(id)), ctx…);
} else {
  _coach.say(CueType.praise, VoiceContent.pool(script.praisePool), ctx);  // truly clean
}

🧒 what changes

Today: "rep ended → look back → say the fault." Target: "fault detected mid-rep → say it now." The count and the praise still happen at rep-end (nothing else knows the rep number, or that the whole rep stayed clean). Only the two fault cues move earlier.

03 The tempting wrong turn

Why we do not read resultIssues.instructions

The obvious mid-rep signal is the on-screen instruction map the metrics write to. It's the wrong currency for a typed cue, for three reasons — all verified in the glute-bridge metrics:

FaultKnown whenIn instructions map?Carries critical/soft?
hyperextensioncontinuous (ascend/top)yes — key 'HipExt'no
neck-liftcontinuous (all phases)yes — key 'NeckHead'no
knee-angle hintbottom / setup onlyyes — 'KneeAngle' — but it's a setup hint, not a rep faultno
insufficient hip-extensionpeak (rep end)no—
knee severity (err vs warn)peak (rep end)no—
speed controlpeak (rep end)no—
  1. No affectsForm. The map is phase → type → message (all strings). From it you cannot tell a criticalFault from a softFault — and the same metric flips between them by severity (knee <60° critical, warning soft).
  2. Ad-hoc keys. 'HipExt', not hyperextension — a third casing variant of the F1 trap.
  3. Most faults aren't in it. Three of six are peak-measured and simply don't exist until the top/end of the rep.

📝 your note — the ad-hoc keys & snake_case

Exactly, and it's the reason we don't read this channel. Those keys ('HipExt' …) only ever mattered when the coach matched RepLog fault ids through script.faultIds — the F1 casing trap. This design reads FaultRecord.type instead (already snake_case), so their casing is now a display-layer tidiness issue, not a correctness one — nothing the coach ever touches. Snake-casing them (rename the four addInstruction type strings) is a cheap, isolated cleanup, but it's out of this scope. My call: leave them for now, log a follow-up to fold into a "snake_case the whole vocabulary" pass — not bundled into the real-time change, so this diff stays about one thing.

04 The proposal

Read the metrics' own FaultRecords, via one generic getter

The metrics already build the exact structured object we need — FaultRecord (id + affectsForm + voiceMessage + priority) — and stash it in their faults list the instant they detect. We just expose that generically so the exercise-agnostic adapter can read it.

lib/exercise/exercise_base.dart — new, additivedefault empty
/// Faults known SO FAR in the rep-in-progress, the instant a metric detects
/// them. Default empty: an exercise that hasn't opted in simply never fires a
/// real-time cue and keeps the post-rep RepLog path. Read-only; no pipeline change.
List<FaultRecord> get liveFaults => const [];
lib/exercise/glute bridge/glute_bridge.dart — overrideglute-bridge scope
// The metrics' own live accumulation. Continuous faults (hyperext, neck) appear
// here mid-rep; each is added once per rep and cleared at rep boundary by
// resetAndCountFault(). See the timing note (§05) for peak faults.
@override
List<FaultRecord> get liveFaults => [for (final m in _metrics) ...m.faults];

✔ why this beats a static key→type map

FaultRecord carries affectsForm, so critical-vs-soft is read straight off the fault, not guessed from a metric name — and it handles the severity-varying metrics (knee, hip-ext) correctly. It's also the same currency the post-rep path already uses, so both channels agree on fault ids.

05 The subtlety that shapes everything

Peak faults are gone before the coach runs

The voice frame runs after the exercise has processed the pose. On the rep-completing frame the exercise does all of this, in order, inside _onRepCompleted — and the last step wipes the metrics:

repCount += 1
the rep is now "landed"
checkRepCompletion()
peak faults (hip-ext, knee, speed) get added to metric.faults
addRepLog(...)
RepLog captures ALL faults (continuous + peak) — this is the durable record
resetAndCountFault()
clears metric.faults → liveFaults is now empty

Then coach.processFrame runs. So on the completing frame, liveFaults is already empty — the peak faults only ever existed for a few lines inside the exercise. The consequence:

Fault kindFires viaWhen it's heard
Continuous — hyperext, neckliveFaults (real-time)mid-rep, the instant detected
Peak — hip-ext, knee, speedRepLog (post-rep, as today)at rep-completion

💡 this is the honest reading of "real-time"

"Fire the instant it's known." A peak fault is not knowable before the peak, so it can't fire earlier — it lands at rep-end and that's correct, not a compromise. The win is that the continuous faults (the ones you can fix mid-rep — "đừng ưỡn lưng", "đặt đầu xuống") now fire while the user can still act on them. The hybrid isn't a workaround; it's the shape of the problem.

06 The logic

What the adapter does each frame

Two paths, one shared per-rep memory so a fault never speaks twice. The order matters.

A · every activated frame — drain liveFaults
For each fault in exercise.liveFaults whose type is not yet in _spokenThisRep: say criticalFault if affectsForm, else softFault; add the type to _spokenThisRep. Uses rep-in-progress number (repCount + 1).
B · on repCount++ — the rep-landed path
(1) count as today. (2) For each RepLog fault not already in _spokenThisRep → say it now (this is where the peak faults land). (3) If the rep saw zero faults (nothing spoken, RepLog clean) → praise.
C · rep boundary — reset per-rep memory
Clear _spokenThisRep when the rep number advances, so next rep starts fresh. Cross-rep fault persistence (for critical escalation) keeps its own _faultFirstSeenRep map, as today.

⚠ the two things I'd get wrong first — flagging for review

Rep numbering. A live fault fires while repCount is still the previous value, so the cue's repNumber must be repCount + 1 — otherwise the policy's one-outcome-per-rep guard (_lastOutcomeRep) won't line up with the count/praise that fire at rep-end on the same rep, and a faulted rep could still get praised.

Order within the frame. Path A must run before path B on the completing frame, so a continuous fault already spoken live isn't re-spoken from the RepLog. _spokenThisRep is the dedup.

🧒 the whole thing in one line

"Say a fault the moment a metric sees it; remember you said it; at rep-end, mop up any fault that was only knowable at the end; and if nothing at all went wrong, praise."

08 Your call

Open questions before Codex builds

Everything above I'm confident in. These three I want your ruling on — annotate or reply.

Q1 · soft mid-rep

Soft faults fire mid-rep — is that the UX you want?

You said "both real-time." A critical mid-rep cue ("đừng ưỡn lưng") is clearly useful while moving. A soft one ("nâng hông cao hơn chút") interrupts the rep for a non-urgent nudge. Confirm:

ASoft fires real-time too, as decided — hunger+base keeps it sparse. (Your stated call.) BCritical real-time, soft stays post-rep — real-time reserved for what you can act on immediately.

Q2 · faults during the bottom/setup phase

Neck-lift is detected even while lying at the bottom. Speak it then?

The neck metric runs in onBottomFrame too, so a lifted head between reps shows up in liveFaults during the bottom phase (no rep in progress yet).

ASpeak it — a lifted head during setup is worth a nudge; feels attentive. BSuppress until the concentric starts — only cue faults during an actual rep.

Q3 · the one base-class addition

Is the liveFaults getter on ExerciseBase acceptable?

D1's rule was "zero changes to the pipeline." This adds a read-only getter (default empty) — not a frame-flow change, but it is new base surface. My read: it's the minimum honest way to give the generic coach a typed mid-rep signal, and it's inert for every exercise that doesn't override it. Veto if you'd rather keep the signal entirely inside glute bridge (would mean a glute-specific coach subclass instead).
