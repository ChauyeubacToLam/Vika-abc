01 The ask

Goal & what's already locked

Rebuild hustle as an effort cue, not a rep-counter cue. It arms when the user hesitates between reps (the inter-rep gap stretches past this set's own baseline) and fires only at the first entry into the exercise's declared effort phase after that gap — the force moment the user just committed to (glute bridge: the raise). Speaking never happens mid-gap, and structurally never after a set ends. This is the 07-09 decision plus its lavish-review refinements (decisions.md, both 07-09 hustle entries); do not re-litigate them. This doc designs their implementation.

Locked · armThe inter-rep gap stretching past the set's baseline (median of the first 2–3 gaps) arms hustle. It is a behavioral "do I go again" signal, not a fatigue meter. Never spoken mid-gap.
Locked · fireThe armed cue rolls at entry into the exercise's declared effort phase (VoiceScript.effortPhaseKeys) — the push tracks force, not rep topology (review generalization). Glute bridge: the raise, which is also its first movement phase — a topology coincidence. Squat, when it migrates: the ascent, not the descent-start. No next rep → no fire.
Locked · void-on-absencePresence-loss or pause during an inter-rep gap VOIDS it: cannot arm hustle, excluded from the baseline median (review rule). An out-of-frame errand and a walk-away rest are indistinguishable — both kill the "hesitating in position" read.
Locked · paired finishSecond flavor (review Q1): when the count anchor fires with exactly ONE rep remaining (rep N−1 lands), the push MAY pair in the same breath ("Chín — cố lên!" / "Một cái nữa thôi!"). Stochastic quiet-side roll, rotating final pool, NEVER deterministic. A fired pairing consumes the push for that transition.
Locked · probabilityPersistence-shaped, no per-set cap. First hesitation = low odds; stacking hesitations climb; firing resets. A grinding finish can earn 2+ pushes. Base quiet-side, personality scalar applies.
Locked · honesty"Một cái nữa thôi!" only when targetReps proves the final rep; otherwise "Cố lên!". Rep-duration slowdown is not a trigger (bodyweight).
Locked · slotLowest outcome priority, never the second in-rep slot (per-moment exclusivity, collision gap). Strict perishability (review Q3): an armed push drops if the sink is busy at the fire moment. The next-rep reminder outranks hustle where they share the commit edge (§05).
Locked · ships OFFNumbers stay symbolic. Nothing plays until the gap thresholds are calibrated from real ExerciseLogger timestamps and the audio is recorded. Pilot: glute bridge.

The design problem is not "what should hustle do" — that's settled. It's three things the decision left to the build: (1) can we observe the effort-phase entry and the gap at the adapter seam at all; (2) which layer owns the gap math versus the probability; (3) how we get from "no timestamps in any log today" to three calibrated numbers.

03 The observability question

Can the adapter even see the effort-phase entry and the gap?

The whole design hinges on this. If the effort-phase entry and the inter-rep gap are not cleanly observable at the adapter seam, everything else is moot. Three findings, all verified against the code.

Finding A — the effort-phase entry is already observable, no new base surface

The adapter reads exercise.currentPhaseKey every activated frame today (it's how phase cues work). For glute bridge that key is the state-machine name: bottom → ascending → topHold → descending. The fire moment (review generalization: entry into the exercise's declared effort phase — the force moment, not "rep start") is exactly currentPhaseKey entering the ascending phase. On glute bridge the effort phase IS the rep's first movement phase, so this edge is also the rep-start commit edge — a topology coincidence, not the definition. (Squat, when it migrates: rep starts with the descent, but the push belongs on the ascent.)

lib/voice/policy_voice_coach.dart — _maybeSpeakPhaseCue (proof the phase key is in hand)already read every frame
final cueKey = script.phaseCues[exercise.currentPhaseKey];  // opaque string, adapter already has it

So the adapter can detect the effort-phase entry with zero new ExerciseBase surface — it just needs to know which opaque key means "the force phase is now underway." That identity is exercise-specific (glute's effort phase is ascending; squat's would be its ascent), so it belongs in the content layer next to phaseCues, not baked into the agnostic adapter: a Set<String> effortPhaseKeys on VoiceScript, which the glute factory sets to {'ascending'} and nobody else sets. Empty = this exercise never arms hustle (the switch).

✔ why VoiceScript, not a new ExerciseBase getter — RESOLVED (review Q4)

Nam decided Q4 with the generalization: the declaration lives on VoiceScript. The 07-09 real-time-cue design already paid for one additive base getter (liveFaults); this needs zero more — the phase key is already surfaced, phaseCues is precedent for phase semantics in the content layer, and squat's non-migration stays a default no-op: squat simply doesn't set effortPhaseKeys, so the arming code never runs for it.

Finding B — the gap must be timed on the pose clock, and it is available

The inter-rep gap is a property of the movement timeline, not the audio timeline. The exercise already stamps every frame with a pose clock the adapter can read:

lib/exercise/exercise_base.dart — the frame clock (public, already there)gap timing source
int get frameTimestampMs => frameTimestamp.millisecondsSinceEpoch;  // same clock the state machine times reps on

Timing the gap on exercise.frameTimestampMs (rather than the policy's wall clock, which the collision gap uses) keeps the measured gap identical to the gap the exercise itself experienced — robust to pipeline lag / dropped frames, because both use the same per-frame stamp. Two clocks, each for the right physical quantity: pose clock for the inter-rep gap, audio/wall clock for the collision gap.

Finding C blocker for calibration — no log holds a timestamp today

This is the finding that shapes the rollout. RepLog carries repNumber, correctForm, and a free-form data map — no timestamp. ExerciseLogger stores none either. Glute bridge's _onRepCompleted receives timestampMs and uses it for speed control, but never logs it.

lib/utils/exercise_logger.dart — RepLog (no time field anywhere)calibration gap
class RepLog {
  final bool correctForm;
  final int repNumber;
  final Map<String, dynamic> data;   // peak angles, fault ids — but NO rep-land / rep-start time
}

💡 consequence: gaps cannot be recovered from existing sessions

The three hustle numbers are supposed to come from real logged rep timestamps — but no logged session, past or present, contains one. So calibration requires a capture step before it can start. The cheapest one that touches nothing risky: have the adapter debugPrint every gap it computes (it computes them anyway). Nam runs a handful of real glute-bridge sets on a debug build and reads the gap distributions off the console. No schema change, no pipeline change. Detail in §06.

04 The measurement

The gap, the baseline, void-on-absence, and the one failure mode

Define the gap from the two observable events. Rep N "lands" when repCount increments (glute counts at descending → bottom). Rep N+1 "starts" when the phase enters the effort key (on glute, the effort phase is the rep's first phase, so effort entry = rep start). The gap that precedes rep N+1 is the rest between them:

the definition (design, not final code)one pose-clock subtraction
// gap(N+1) = time the user spent deciding to go again
gap(N+1) = frameTimestampMs@effortEntry(N+1)  −  frameTimestampMs@repLanded(N)
repCount++ → record land time
On the landing frame, stamp _lastRepLandedAtMs = frameTimestampMs and set _awaitingRepStart = true. State is now bottom (resting).
bottom … bottom (resting)
Frames tick by; nothing fires. This is the hesitation — silent by construction. A paused or person-lost frame here VOIDS the gap (below).
enter effort phase → the commit
When currentPhaseKey enters an effort key AND _awaitingRepStart: compute gap = frameTimestampMs − _lastRepLandedAtMs, clear the flag, then decide.

💡 generalization note — where the collapse stops holding (squat, later)

On glute the gap ends at the same edge the push fires on. On an exercise whose effort phase is not its first phase (squat: rep starts descending, force is the ascent) the two moments separate: the gap must end at the rep-start commit edge (or it would absorb the descent), while the fire moves to the effort entry — an armed flag carried from one edge to the other. That split is deferred until squat migrates; v1 implements only the collapsed glute form. Named here so the migration doesn't silently measure squat gaps through the descent.

Void-on-absence — a gap touched by pause or presence-loss is dead review rule

Presence-loss or pause during an inter-rep gap VOIDS that gap: it can never arm hustle, and it is excluded from the baseline median. An out-of-frame errand and a walk-away rest are indistinguishable, and both kill the "hesitating in position" read — voiding is wrong in neither case. Mechanically the void is one nulled stamp, hooked into the adapter's existing early-return (state != activated || exercise.isPaused || !hasPose):

what clears
_lastRepLandedAtMs = null on every paused / no-pose / not-activated frame (plus a one-shot debug log of the void, for Stage-B visibility). _awaitingRepStart stays latched — it is about the phase edge, not the gap.
what the baseline sees
Nothing. The voided gap is never computed, so it never reaches _recordGapAndLog — the baseline window simply waits for the next valid gap (it closes on the first kBaselineGapCount valid gaps, however long that takes).
what resumes fresh
The first effort entry after the void clears the _awaitingRepStart latch, finds landed == null, and no-ops — no arm, no log. The next rep LAND re-stamps _lastRepLandedAtMs, and gap measurement resumes clean from there.

Nulling on every blocked frame (not just gap-phase ones) is deliberate: a mid-rep pause is harmless to null because the next land re-stamps anyway, and it saves the adapter from having to know whether the exercise was mid-rep or mid-gap when the world went away.

Baseline. Collect the first kBaselineGapCount gaps of the set (placeholder 2, TUNE 2–3) and take their median. Only gaps after the baseline window is closed are arm-eligible — during the window we're still learning the user's rest rhythm. With count 2, the earliest fire is the start of rep 4 (gaps before reps 2 and 3 build the baseline; the gap before rep 4 is the first that can arm). That satisfies the "nothing arms before ~rep 3" cold start automatically.

Arm condition. A post-baseline gap arms iff gap > baseline × kStretchRatio and gap > kMinArmGapMs. The ratio makes it scale-free (a fast rester and a slow rester each get judged against their own rhythm); the absolute floor stops a tiny baseline (e.g. 200 ms) from turning an ordinary 400 ms pause into a "2× stretch."

⚠ numbers most likely wrong — the inflated-baseline failure mode

Named in the spec's own risk list: a hard set whose EARLY gaps are already long inflates the baseline, so hustle never arms on the grind it exists for. A user who is already struggling from rep 2 sets a high baseline, and their rep-9 grind looks "normal" against it. Two honest options:

(a) Accept for v1 — simplest, and the decision explicitly allows "mitigate or explicitly accept." We lose hustle on the already-hard set; we never false-fire. (b) Clamp the baseline to a plausible-rest ceiling (median, then min(median, kBaselineCeilingMs)) so early grinding can't run the baseline away. The ceiling is itself an uncalibrated number. My call: ship (a), but instrument for (b) — the calibration run (§06) logs raw baselines and per-rep gaps, so we'll see whether early-gap inflation is real for glute bridge before adding a knob we might not need.

💡 "arm" and "fire" collapse to one instant on glute — by topology

You cannot know a gap stretched until it ends — and on glute it ends exactly at the effort entry. So there is no mid-gap timer to get wrong: the adapter learns the gap length and decides in the same frame, at the raise. Arm-on-hesitation, fire-on-commit is one evaluation, not two, in the pilot (the generalization note above covers when that stops holding). A hesitation that never resolves into a rep is never evaluated, so it can't climb the persistence counter for nothing — which is the correct reading of "stacking hesitations," since a hesitation only counts if the user then chose to go again.

05 The seam

Arm in the adapter, fire in the policy — reusing hunger

The split follows the existing division of labor exactly. The adapter owns everything exercise-semantic (what a rep-start is, what the gap is, whether it stretched, which line honesty demands). The policy owns the probability — and the persistence climb is already built: it's the per-type hunger counter, which climbs on every eligible-but-silent decide() and resets to zero in _onSpoke. That is precisely "stacking hesitations climb the odds; firing resets them."

Adapter: one shared "rep attempt started" boundary — reminder first, hustle second

On glute bridge the effort entry IS the rep-start commit edge, and a parallel 07-09 decision put the next-rep instruction (reminder) on that same edge — with explicit precedence: the reminder outranks hustle where they share the edge (voice-behavior-spec.md, "next-rep instruction"). So the adapter computes the boundary ONCE and feeds both consumers in rank order. This design does not build the reminder layer (someone else's surface) — it builds the boundary as a single named seam, evaluates hustle there, and leaves an explicit, ordered hook point above it. Where an exercise's effort phase is not its first phase (squat, later), the edges separate and the two cues stop competing.

Arming reduces to "should we even ask the policy at this boundary." If the gap didn't stretch, the adapter doesn't call say(hustle) at all, so the hunger counter isn't touched (neither climbed nor reset) — a normal rep between two hesitations correctly leaves the climb intact.

lib/voice/policy_voice_coach.dart — the shared boundary + arming step (design sketch)runs every activated frame
// called after the rep-land / drain logic, every activated frame
void _onRepAttemptBoundary(ExerciseBase exercise) {
  final effort = script.effortPhaseKeys;
  if (effort.isEmpty) return;                     // exercise opted out (squat, everything non-glute)
  final phase = exercise.currentPhaseKey;
  final enteredEffort = !effort.contains(_lastPhaseKey) && effort.contains(phase);
  _lastPhaseKey = phase;
  if (!enteredEffort || !_awaitingRepStart) return; // only the first effort entry after a landed rep
  _awaitingRepStart = false;
  // >>> THE shared "rep attempt started" boundary (glute: raise entry = commit edge).
  // TODO(wiring): the next-rep reminder evaluates FIRST here and OUTRANKS hustle
  // (spec, Nam 07-09). When that layer lands, hustle below runs only if the
  // reminder did not claim this moment. Do not reorder.

  final landed = _lastRepLandedAtMs;
  if (landed == null) return;                    // rep 1 — and void-on-absence gaps (§04)
  final gap = exercise.frameTimestampMs - landed;
  _recordGapAndLog(gap);                          // calibration capture (§06) — runs even while OFF

  final base = _baselineGapMs;                     // null until the baseline window closes (valid gaps only)
  if (base == null) return;                      // cold start: nothing arms before ~rep 3
  final armed = gap > base * kStretchRatio && gap > kMinArmGapMs;
  if (!armed) return;

  final startedRep = _lastRepCount + 1;            // the rep being committed to
  final isFinalRep = targetReps != null && startedRep == targetReps;
  if (isFinalRep && _finalPushConsumed) return;  // paired push already took this transition (below)
  final pool = isFinalRep && script.hustleFinalPool.isNotEmpty
      ? script.hustleFinalPool          // "Một cái nữa thôi!" — only when the counter PROVES it
      : script.hustlePool;              // "Cố lên!" — generic push
  _coach.say(CueType.hustle, VoiceContent.pool(pool),
      CueContext(repNumber: startedRep, sinkBusy: _coach.isBusy));
}

The paired finish: a roll that rides the N−1 count anchor, then consumes review Q1

Second flavor, resolving review Q1: when rep N−1 lands (exactly one rep remaining) the count anchor fires deterministically (hard rule 3) — and the push MAY pair in the same breath ("Chín — cố lên!" / "Một cái nữa thôi!", target-proven, rotating hustleFinalPool — this is where that pool earns its keep, so it needs ≥2 recorded lines at Stage C for the no-immediate-repeat rotation to bite). Stochastic quiet-side roll, never deterministic — a guaranteed finish line every set is the rejected 07-08 metronome; Nam accepted that condition. It lives in _handleRepLanded, after the count and the fault/praise branches (hustle is the lowest-priority outcome, so it must roll last and lose the moment to any of them via _canStartOutcome):

lib/voice/policy_voice_coach.dart — _handleRepLanded, appended after the outcome branches (design sketch)the pairing + the consume
// countSpoke = the captured return of the count say() above — "same breath" means
// riding an anchor that actually voiced (defensive: final-2 anchors always do).
final oneRemaining = targetReps != null && repCount == targetReps - 1;
if (oneRemaining && countSpoke && script.hustleFinalPool.isNotEmpty) {
  final spoke = _coach.say(
    CueType.hustle,
    VoiceContent.pool(script.hustleFinalPool),   // rotating: "cố lên" / "một cái nữa thôi"
    baseCtx.copyWith(sinkBusy: _coach.isBusy),
  );
  if (spoke) _finalPushConsumed = true;       // a FIRED pairing consumes the final transition —
}                                              // no second fire at the final rep's effort entry

The consume mechanism, explicitly. _finalPushConsumed is a single adapter bool, set only when the paired say returns true (a fired pairing — a rolled-and-lost or slot-blocked pairing does NOT consume; the final effort entry can then still fire if its gap arms). It is read exactly once, at the effort entry whose startedRep == targetReps, where it suppresses the say — the gap is still measured and logged for calibration, only the voice is consumed. It never needs clearing mid-set (it can only matter on the final transition, which is followed by set-end); the begin-set wipe resets it with the rest of the per-set state.

Interplay worth naming: the paired roll goes through the same decide(CueType.hustle, …) as the mid-set flavor, so it shares the hunger counter — a set full of armed-but-silent hesitations makes the finish pairing likelier, and a fired pairing resets the climb. That coupling is deliberate (one probability machinery, one determinism story, and a grinding set earning a likelier finish push is the right feel) but it is a coupling — flagged in the review list below.

Policy: hunger replaces the coin-flip

_hustledThisSet and the isFinalReps gate are deleted. What remains is the slot check plus a hunger-scaled roll — identical in shape to every other stochastic cue:

lib/voice/voice_policy.dart — _hustle() (design target)persistence via existing hunger
bool _hustle(CueContext ctx) {
  if (!_canStartOutcome(CueType.hustle, ctx)) return false;  // lowest priority, never the 2nd in-rep slot
  if (ctx.sinkBusy) return false;                        // perishable: drop at the commit, never queue late
  final t = tuning[CueType.hustle]!;
  final idle = _idle[_key(CueType.hustle, ctx)] ?? 0;    // climbs per armed-but-silent commit; _onSpoke resets it
  return _rng.nextDouble() < _p(t, idle);              // _p applies base + step·idle, then personality, then cap
}

💡 the whole mechanism in one breath

"When the user rests longer than their own rhythm and then goes again, ask the coach if it should push as the force phase begins; the more times that has happened this set without a push, the likelier yes; a push resets the meter; there's no cap, so a real grind can earn two. At the second-to-last count, the coach may also pair a finish push in the same breath — a roll, never a ritual — and if it does, it won't double-dip at the last raise. If the moment's audio slot is busy, the push is dropped, not saved — a late 'one more!' is worse than none. And if the camera lost you or you paused mid-rest, that rest tells us nothing, so it's thrown away."

⚠ the seams I'd get wrong first — review these hardest

1 · Perishable via sinkBusy — RESOLVED strict (review Q3). An explicit ctx.sinkBusy drop (like phase), adapter passes _coach.isBusy, applied to BOTH flavors. Rationale: the collision gap only blocks outcome audio; a short count anchor still playing at the fire moment isn't an outcome, so without the sinkBusy check the push would queue behind it and land a beat late — re-introducing the very "narrating the slack" feel we're avoiding. Nam confirmed strict-drop over queue-slightly-late. One consequence to watch: the paired flavor fires immediately after its own count anchor, so on a slow device the count's audio may still be draining at the paired roll — if Stage-B testing shows the pairing starving, the "same breath" may need to ride the count's queue rather than the busy check. Flagged, not built.

2 · Void-on-absence supersedes the plain pause guard (review rule 5). Pause OR presence-loss during a gap voids it — not just "don't arm" but "don't let it into the baseline" (§04). The false-arm risk (wall-derived frameTimestampMs keeps advancing across a pause → huge resumed gap) and the baseline-poisoning risk (a 30 s walk-away entering the median) die together. The nulled-stamp mechanism and the resume path are specified in §04.

3 · Aborted rise (twitch-up, drop back). Glute's state machine can go ascending → bottom (abort, no rep). That's an effort entry with no landed rep after it. The _awaitingRepStart latch handles it: it's cleared on the first effort entry after a land, so a re-rise doesn't re-fire. A twitch only ever fires if the gap before it was already stretched — rare, and accepted for v1. Worth a targeted test.

4 · The two flavors share one hunger counter. The paired roll and the mid-set roll both go through decide(CueType.hustle, …), so hesitation climb inflates the finish-pairing odds and either fire resets both. Deliberate (one machinery, right feel) — but if Nam ever wants the finish pairing's odds independent of the set's hesitation history, it needs its own flat roll, which is a policy change, not an adapter tweak. Also note the edge: at targetReps == 2 the pairing is eligible at rep 1's land, before any baseline exists — legal per the rule (it's structural, not gap-conditioned), quiet-side roll anyway.

Open questions — all resolved in Nam's lavish review (07-09)

All four were ruled on with Fable 07-09 (decisions.md, "Hustle lavish-review refinements"; voice-behavior-spec.md hustle section + hard rule 8 carry the canonical wording). The cards stay as the reasoning trail — each carries its resolution.

Q1 · the "Chín — cố lên!" pairing changes shape — RESOLVED: second flavor added

Commit-firing means the count and the push no longer land together

In the old post-rep model, count + hustle fired at the same instant ("Chín — cố lên!"). In the commit-fired model, the count for rep 9 fires when rep 9 lands at the bottom, and the push fires when rep 10 starts at the raise — on either side of the hesitation. So they're sequential now: "Chín… [rest]… Một cái nữa thôi!". The co-occurrence machinery is preserved (count is not an outcome cue, so it never blocks or is blocked by hustle) — but in glute's timing they simply happen at different moments.

ASequential is correct and better — it mirrors a real coach: count the rep, watch the hesitation, then push into the commit. (My read.) BYou actually want them simultaneous — then hustle would need a different moment, which reopens the commit-fired decision. Flag it.

✔ Nam's ruling — neither A nor B: both, as two flavors

The hesitation-armed effort-entry push stays exactly as designed (sequential). AND a second flavor restores the same-breath finish energy without reopening the commit-fired decision: when the count anchor fires with exactly ONE rep remaining, the push MAY pair in the same breath — a stochastic quiet-side roll on the rotating hustleFinalPool, NEVER deterministic (a guaranteed finish line every set is the rejected 07-08 metronome; Nam accepted that condition). A fired pairing consumes the push for that transition — no second fire at the final rep's effort entry. Mechanism: §05 "The paired finish."

Q2 · the inflated-baseline failure mode — RESOLVED: option A

Accept it for v1, or clamp the baseline now?

A set that's hard from the first rep inflates its own baseline, so the grind never reads as stretched and hustle stays silent on exactly the set it's for (§04).

AAccept for v1, instrument, revisit with Stage-B data — we never false-fire, and the calibration run will show whether it's real before we add a knob. ← Nam's ruling. BClamp the baseline to a ceiling now — costs one more uncalibrated number up front.

Q3 · perishability strictness — RESOLVED: option A, strict drop

Drop the push if any audio is mid-word at the commit, or only if an outcome line is?

Strict (my design): add ctx.sinkBusy so a push is dropped even behind a short count anchor — never late. Loose: rely only on the outcome collision gap, letting a push queue briefly behind a non-outcome line.

AStrict drop — a late "one more!" is worse than none; the armed gap is long so this rarely binds anyway. ← Nam's ruling: an armed push drops if the sink is busy at the fire moment. BLoose — let it queue behind a count so a valid push isn't lost to a coincident number.

Q4 · phase identity on VoiceScript — RESOLVED: yes, renamed effortPhaseKeys

Is the phase-identity declaration on VoiceScript the right home?

It keeps ExerciseBase untouched and makes squat's non-migration a no-op, but it does put a sliver of movement semantics into the content layer next to phaseCues. The alternative is a new ExerciseBase getter (e.g. bool get repInProgress). My read: VoiceScript is cheaper and already holds per-exercise phase config.

✔ Nam's ruling — VoiceScript, plus a generalization the draft missed

Home confirmed: VoiceScript (zero ExerciseBase surface, squat neutralization stays a default no-op, phaseCues precedent). And the semantics generalize: the fire moment is entry into the exercise's declared EFFORT PHASE, not "rep start" — the draft's "rise = rep start" was a glute-bridge topology coincidence. Renamed risePhaseKeys → effortPhaseKeys everywhere. Glute bridge: the raise (identical behavior to the draft). Squat when it migrates: the ascent, NOT the descent-start — the push tracks force, not rep topology. Where effort phase ≠ first phase, hustle's edge separates from the next-rep reminder's commit edge and the two stop competing (§05).
